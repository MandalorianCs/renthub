# Как перенести связку с Telegram в другой проект

Здесь собрано всё, что понадобилось в RentHUB, и отмечено, что зависит от
Supabase, а что верно для любого бэкенда.

Связка состоит из **трёх независимых частей**. Их можно брать по одной, и
порядок именно такой: без первой не работают две остальные.

| Часть | Что даёт | Зависит от |
|---|---|---|
| 1. Привязка | у человека в базе появляется `telegram_id` | ничего, кроме таблицы пользователей |
| 2. Уведомления | события из базы приходят человеку в Telegram | таблица `notifications` |
| 3. Коды входа | вход в приложение по коду вместо SMS | Supabase Auth (Send SMS Hook) |

---

## Ограничение, из которого следует вся архитектура

**Бот не может написать первым.** Telegram запрещает боту отправлять
сообщение тому, кто сам не начинал с ним диалог. Это не настройка и не
обходится ничем.

Отсюда:

- сценарий всегда начинается со стороны человека — он открывает бота;
- ссылку на бота нужно держать на видном месте в приложении и на сайте;
- «введите номер, и придёт код» работает только для тех, кто уже открыл
  бота хотя бы раз;
- уведомление для непривязанного человека не теряется, а ждёт в базе —
  и приходит пачкой сразу после привязки.

---

## Часть 1. Привязка номера

### Что нужно в базе

```sql
alter table users add column telegram_id bigint unique;
alter table users add column telegram_username text;
create index users_telegram_idx on users (telegram_id) where telegram_id is not null;
```

`unique` обязателен: один чат — один аккаунт. Без него человек привяжет свой
Telegram к двум аккаунтам и будет получать перемешанные уведомления.

### Как это работает

Бот показывает кнопку `KeyboardButton(request_contact=True)`. Человек нажимает
— Telegram присылает контакт с номером, **который он проверил при
регистрации**. Это сильнее SMS-кода: код доказывает владение симкой в момент
ввода, а Telegram хранит эту связь давно.

### Проверка, без которой всё ломается

```python
if contact.user_id != message.from_user.id:
    # чужой контакт — переслать можно любой
    return
```

Telegram позволяет **переслать боту чужой контакт**. Без этой строки любой
привяжет к своему чату чужой номер и будет получать чужие уведомления о
сделках. Это самая важная строка во всей привязке.

### Нормализация номера

Правило приведения номера к E.164 должно быть **одним и тем же** в боте, в
приложении и в служебных скриптах. В RentHUB оно продублировано в трёх местах
(`bot/bot.py`, `src/lib/auth.tsx`, `scripts/invite.mjs`) и это записано
комментарием в каждом: разойдутся — человек с верным номером не найдёт свой
аккаунт, а причину будут искать в Telegram.

## Часть 2. Уведомления

### Что нужно в базе

```sql
create table notifications (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users (id) on delete cascade,
  type text not null,
  title text not null,
  body text,
  read_at timestamptz,
  sent_at timestamptz,          -- ключевая колонка: отметка доставки ботом
  created_at timestamptz not null default now()
);
```

Смысл в том, что **уведомления создаёт база**, а не приложение: триггеры и
планировщик пишут строки, бот их разносит. Тогда приложение и бот — два окна
в одни данные, а не два источника правды.

### Цикл доставки

Бот раз в N секунд забирает строки с пустым `sent_at`, отправляет и ставит
отметку. Порядок «отправить → отметить» выбран сознательно: при падении между
шагами человек получит уведомление дважды. Обратный порядок терял бы его
молча, а повтор заметен и безобиден.

Строки для непривязанных пропускаются **без отметки** — придут после привязки.

### Зачем боту служебный ключ

Он пишет в чужие строки (`telegram_id`) и отмечает доставленные уведомления —
обе операции невозможны от имени пользователя при включённом RLS. Отсюда:
бот запускается там, где вы контролируете машину, а ключ лежит в файле вне
репозитория.

## Часть 3. Коды входа вместо SMS

Это часть, которая экономит деньги: SMS-провайдер для Казахстана требует
$250/мес только за регистрацию имени отправителя.

### Идея

Supabase **сам** генерирует код, сам его проверяет и сам считает попытки.
Наружу отдаётся только доставка — через Send SMS Hook. Приложение при этом не
меняется вообще: там остаётся тот же `signInWithOtp({ phone })`.

Своя реализация кодов означала бы своё хранилище, свои сроки жизни и свою
защиту от перебора — всё это пришлось бы поддерживать рядом с готовым.

### Что делает функция

1. Проверяет подпись запроса (`standardwebhooks`, секрет вида `v1,whsec_…`,
   префикс перед проверкой срезается).
2. Приводит номер к E.164 — **GoTrue отдаёт его без плюса**, а в базе он с
   плюсом. Без приведения не найдётся никто, и все получат «Telegram не
   привязан» при полностью исправной привязке.
3. Ищет `telegram_id` по номеру служебным ключом.
4. Отправляет код через Bot API.

Полный код — `supabase/functions/telegram-otp/index.ts`.

### Развёртывание

GitHub-интеграция Supabase применяет **только миграции**. Функцию нужно
разворачивать руками:

```bash
npx supabase login
npx supabase link --project-ref <ref>
npx supabase functions deploy telegram-otp --no-verify-jwt
npx supabase secrets set "SEND_SMS_HOOK_SECRET=v1,whsec_..." "TELEGRAM_BOT_TOKEN=..."
```

`--no-verify-jwt` обязателен: хук вызывает функцию от имени платформы, а не
пользователя, и проверка пользовательского токена отклонила бы каждый вызов.

Дальше в панели: **Authentication → Hooks → Send SMS** — тип HTTPS, адрес
функции; панель покажет секрет. И **Providers → Phone** — включить.

### Побочное свойство, которое стоит осознать

Пилот остаётся закрытым сам собой: код уходит только тому, у кого есть
`telegram_id`, а он появляется лишь после «Поделиться номером» у заведённого
участника. Отдельный «список допущенных» вести не нужно — его роль играет
сама привязка.

## Что копировать

| Файл | Часть |
|---|---|
| `bot/bot.py` | 1 и 2 целиком |
| `bot/requirements.txt`, `bot/.env.example` | запуск бота |
| `supabase/migrations/20260819100000_telegram_link.sql` | колонки и приватность |
| `supabase/functions/telegram-otp/index.ts` | 3 |
| `scripts/notify-test.mjs`, `scripts/notify-clear.mjs` | проверка цепочки без реальных событий |

## Чего не делать

**Не двигать бизнес-логику в бота.** Переходы статусов в RentHUB живут в RPC
Postgres и опираются на `auth.uid()`, которого у служебного ключа нет.
Соблазн сделать «подтвердить бронь» кнопкой в Telegram через обёртку с
`user_id` аргументом велик — и это ровно тот случай, когда правило,
проверяемое в двух местах, однажды разъедется молча.

Правильный путь: бот получает пользовательский токен через админ-API и ходит
в базу как сам человек. Тогда работают и RLS, и `auth.uid()`, и правило
остаётся одно на приложение и бота.

## Как проверять, что всё живо

Цепочка состоит из четырёх звеньев: запись появилась → бот её увидел →
Telegram принял → человек получил. Когда скажут «уведомления не приходят»,
нужно знать, какое звено молчит. Для этого есть отдельная команда, которая
кладёт в базу проверочную запись:

```bash
npm run notify:test -- +7701...
npm run notify:clear
```

Проверять на живой сделке дорого: её пришлось бы создать, провести и закрыть.
