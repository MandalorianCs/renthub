## Как здесь всё устроено

**Бизнес-правила живут в Postgres**, а не в React: позже подключится
Telegram-бот, и правило в компоненте он обойдёт. Переходы статусов — только
через RPC, суммы проставляет триггер из цены объявления, пороги в
`app_settings`.

**Схема разворачивается пушем в `main`** — подключена GitHub-интеграция
Supabase. Отсюда правило: **не менять схему через SQL Editor**, иначе
следующий деплой падает с ошибкой синхронизации.

**Перед каждым пушем прогонять стенд.** Он поднимает чистый Postgres в
Docker, накатывает миграции и проезжает четыре сценария с включённым RLS:

```
npm run test:db
```

**Сайт собирается при пуше** — GitHub Actions (`.github/workflows/pages.yml`)
запускает `npm run build:pages` и публикует результат. Отдельно коммитить
`docs/` больше не нужно: сайт всегда собран из того кода, что лежит в `main`.
Папки `docs/` в репозитории **больше нет** — 05.09.2026 источник
публикации переключён на «GitHub Actions», и брать сайт из ветки стало
некому. Вместе с папкой ушло правило «пересобери `docs/` тем же
коммитом»: забывать теперь не о чем.

Проверить, что на адресе именно то, что в `main` — `npm run health`,
строка «публикация». Она сравнивает отпечаток коммита, вшитый в страницу
при сборке, с локальной историей.

~~**Переключить настройку Pages**~~ — **сделано 05.09.2026.** Сайт
публиковали ДВА процесса сразу: наш workflow (сборка из кода) и встроенный
«pages build and deployment», бравший папку `docs/` из ветки. У обоих

Отдельно поучительно, чем это держалось. HANDOFF четыре дня утверждал, что

Теперь есть чем: `npm run pages` показывает источник и историю запусков, а

**Локальная работа и публичный адрес — один проект.** Продукт смотрят по

dev-сервере: работа, оставшаяся в рабочем дереве, для пилота не

- держать `.env` и дефолты в `.github/workflows/pages.yml` одинаковыми.
  Разойдутся — локальная сборка перестанет соответствовать опубликованной,
  причём молча. Проверено 31.08.2026: `EXPO_PUBLIC_TELEGRAM_BOT` была
  только в CI, локально работал дефолт из `src/lib/supabase.ts`.

Всё, что ходит в базу мимо RLS, требует секретного ключа — от `seed:users`
и `whoami` до `bot`. Считать их по порядку в списке не надо: признак в том,
что команда читает или пишет чужие строки. Ключ лежит в `.env.secret` —
файл в `.gitignore`, сборка Expo его не читает:

```
SUPABASE_SECRET_KEY=sb_secret_...
```

Разово перебивается переменной окружения:

```
$env:SUPABASE_SECRET_KEY="sb_secret_..."; npm run invite -- +7701... "Имя"
```

Сборка в облаке не видит `.env` — он в `.gitignore`, а EAS забирает проект по
git. Переменные лежат в окружениях EAS, профили в `eas.json` ссылаются на них
полем `environment`. Один раз выложить и проверить:

```
eas env:push preview --path .env --force
eas env:list preview
```

## Как запускать бота

`npm run bot` держится ровно столько, сколько живёт окно, из которого
запущен. Агент, запустивший его фоновой задачей, увидит в журнале
«Run polling for bot @renthub_kokshetau_bot» — а через секунду процесс
умрёт вместе с задачей, и код выхода будет 127. Выглядит как падение бота,
хотя бот тут ни при чём.

Чтобы процесс пережил сессию, его надо отсоединить:

```powershell
$root = "C:\Мои проекты\Startup orda\Никита\renthub"
Start-Process python -ArgumentList "bot/bot.py" -WorkingDirectory $root `
  -WindowStyle Hidden `
  -RedirectStandardOutput "$root\bot\bot.log" `
  -RedirectStandardError  "$root\bot\bot.err.log"
```

Проверить, что поднялся: `npm run health`, строка «бот» — она читает
отметку живости, которую он ставит после каждой волны доставки.

**Экземпляр должен быть один.** 05.09.2026 их оказалось два: вчерашний
никто не остановил, а сегодняшний запустили поверх. Telegram отдаёт
`getUpdates` только одному, второй получает 409 и не видит нажатий. Но
доставку уведомлений делают оба — она идёт через базу, а не через
polling, — и два процесса могут взять одну запись до того, как первый
проставит `sent_at`. Человек получит одно уведомление дважды.

Найти лишние:

```powershell
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Where-Object { $_.CommandLine -like '*bot.py*' } |
  Select-Object ProcessId, CreationDate
```

## Чего агент делать не должен

- **Не печатать `sb_secret_` и не писать его в репозиторий.** Сам ключ лежит
  в `.env.secret`, скрипты читают его оттуда — значит запускать `invite`,
  `moderator`, `demo:fill` и `notify:test` агент может сам, не видя значения.
  Запрет с 21.08.2026 касается только разглашения: не выводить в консоль,
  не коммитить, не пересылать.
- **Коммитить и пушить агент может сам** (разрешено 21.08.2026), но перед
  пушем миграций обязателен `npm run test:db`: пуш применяет схему к живой
  базе, и отменить это одним нажатием нельзя.
- **Пока миграция ждёт стенда — ветка заморожена.** `git push` отправляет
  ветку целиком, а не последний коммит. Коммит поверх непроверенной
  миграции и невинный пуш уносят в живую базу обоих. Проверено на себе
  28.08.2026: уехала непроверенная `20260828120000_block_hides_items`.
  Правильно — держать такую миграцию в отдельной ветке
  (`git switch -c migration/имя`) и вливать её в `main` после зелёного
  стенда. Тогда работа в `main` не блокируется сломанным Docker.
- **Не писать телефоны и ключи в репозиторий** — он публичный.
- **Не менять схему через SQL Editor** — только новой миграцией и пушем.
- **Не ставить UI-киты** (Tamagui, gluestack, Material): они принесут свой
  визуальный язык вместо бренда из деки. Из открытого кода берём поведение
  и ресурсы, не внешний вид.

## Особенности окружения

- Терминал часто открывается в папке выше — перед npm-командами `cd` в
  `renthub`.
- Docker Desktop падает из-за компонента Docker AI (Inference manager) —
  повторяется регулярно. `EnableDockerAI` в настройках стоит `false`, но
  менеджер всё равно стартует и спотыкается об остаток сокета
  `%LOCALAPPDATA%\Docker\run\dockerInference`: Windows отвечает «файл
  недоступен системе» и не даёт его удалить ни обычным путём, ни через
  `\\?\`, ни после `wsl --shutdown`.

  **Причина найдена 31.08.2026.** `dockerInference` — не обычный файл, а
  AF_UNIX-сокет; в Windows это reparse point (атрибут `ReparsePoint`,
  режим `-a---l`, размер 0). После аварийного завершения объект остаётся,
  и держит его драйвер ядра `afunix.sys`, а не процесс. Поэтому его не
  берёт ничто: ни `Remove-Item`, ни `\\?\`, ни `fsutil reparsepoint
  delete` — все получают ошибку 1920 (`ERROR_CANT_ACCESS_FILE`). Папка при
  этом исправна: обычный файл в ней создаётся и удаляется.

  **Обход, который работает без перезагрузки.** Застрявших сокетов больше
  одного, и Docker падает на них по очереди: уберёте первый — упрётся во
  второй. Убирать надо обе папки сразу:

  ```
  %LOCALAPPDATA%\Docker\run
  %LOCALAPPDATA%\docker-secrets-engine
  ```

  Порядок: закрыть процессы Docker, переименовать обе папки (Docker создаст
  новые), запустить Docker Desktop. Проверено 31.08.2026 — движок поднялся
  без перезагрузки, стенд прошёл.

  Точную причину падения показывает лог, а не диалог:
  `%LOCALAPPDATA%\Docker\log\host\com.docker.backend.exe.log`, искать
  `backend crashed`. Именно так выяснилось, что после первой папки Docker
  начал падать уже на Secrets Engine.

  Кнопку **Reset to factory defaults** в диалоге не нажимать: она сотрёт
  образы и контейнеры, а причина не в них.

  Без Docker не работает `npm run test:db`, а значит нельзя пушить
  миграции — правило «сначала стенд» держится именно на нём.
- SMS-провайдер не подключён и не нужен: для Казахстана Twilio требует
  $250/мес только за регистрацию имени отправителя, а Telegram даёт более
  сильное подтверждение бесплатно. В `.env` и в дефолтах `pages.yml` стоит
  `EXPO_PUBLIC_AUTH_MODE=sms` — код приходит в Telegram через
  `telegram-otp`, а не эсэмэской. Дефолт в коде (`app/sign-in.tsx`) и в
  `.env.example` остался `invite`: без переменной приложение открывается на
  вкладке приглашений, и это правильно для того, кто клонировал репозиторий
  и ещё ничего не развернул.
- **Бот не поднимается сам.** Он живёт отдельным процессом, и после
  перезагрузки компьютера его надо запустить руками: `npm run bot`.
  Симптом, если забыть, — `/start` не отвечает, а уведомления копятся в
  базе с пустым `sent_at` и приходят пачкой после запуска. Проверить, жив
  ли он: в логе при старте должно быть `Run polling for bot @…`.
- Бот работает отдельным процессом и держит секретный ключ: `bot/.env`
  (только токен Telegram) плюс корневые `.env` и `.env.secret`. Пока окно с
  ботом закрыто, уведомления копятся в базе и придут после запуска.

## Ограничение хостинга, о котором надо знать

**Path-адреса карточек отдают HTTP 404.** Проверить:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://mandaloriancs.github.io/renthub/app/item/64a6fde6-1fcd-4d8c-bb41-059dc2086620
```

Для человека всё открывается: GitHub Pages отдаёт `404.html`, внутри
которого лежит приложение, и expo-router разбирает адрес сам. Но статус
остаётся ошибкой, и это не чинится кодом: статический хостинг не умеет
отвечать 200 на маршруты, которых нет файлами.

**Мы такие ссылки больше не рассылаем** — с 05.09.2026 и бот, и кнопка
«Поделиться» шлют `/app/?item=<id>`, а он отдаёт 200 вместе с og-тегами.
Карточку открывает каталог, прочитав параметр. Ниже — про то, чем 404
остаётся платой, а чем перестал: превью в мессенджере теперь строится с
живого адреса, а вот прямые ссылки, набранные или сохранённые раньше,
по-прежнему приходят к 404 — для человека незаметно, для краулера нет.

Чем это платится сегодня: поисковики не индексируют страницы объявлений.
На пилоте из одного города это не тот канал, которым он растёт, — растёт
он лендингом и пересылкой ссылок, а превью в мессенджере работает,
og-теги в `404.html` вставляет `build-pages.mjs`.

Чем это станет платиться, когда объявлений будут сотни: витрина не
попадёт в поиск целиком. Лечится переездом на хостинг с переписыванием
адресов — Vercel, Netlify, Cloudflare Pages: там правило «всё, что не
файл, отдавать index приложения со статусом 200» настраивается одной
строкой. Менять код при этом не придётся.

## Чему научил 04.09.2026

**Замер отменил «улучшение», которое сломало бы работающее.** Встроенный
аудит Supabase советует включить Leaked Password Protection — проверку
пароля по базе утечек HaveIBeenPwned. Совет разумный, включение — один
переключатель. Прежде чем нажать, я проверил, что станет с паролями,
которые выдаёт `npm run invite`: сгенерировал 25 таких же и прогнал через
HIBP по k-anonymity (наружу уходит пять символов хеша, пароль — нет).

В утечках нашлись **семь из двадцати пяти**. То есть включение отклоняло бы
примерно каждое четвёртое приглашение, и организатор упирался бы в отказ на
ровном месте.

Заодно выяснилось, что чинится это длиной: 8 цифр — 3–7 из 25 в утечках,
10 цифр — 1, 12 цифр — **ни одного**. Пароль в `invite.mjs` теперь
двенадцатизначный, а диктуемость вернули группировкой: «4827 3619 4823»
произносится как номер карты, то есть легче восьми цифр подряд. В поле
вводится слитно, поэтому печатаются обе формы.

Leaked Password Protection остаётся **выключенной намеренно**, а не по
недосмотру: даже с двенадцатью цифрами она однажды отклонит валидный
пароль, а объяснить это организатору будет некому.

**Проверка нашла дефект в том, что её обслуживает.** `npm run check:errors`
сверяет ограничения базы с таблицами переводов в боте и приложении: без
перевода человек видит `violates check constraint "bookings_check1"` —
не сообщение об ошибке, а улику. Первый же запуск нашёл одиннадцать таких,
включая попытку забронировать собственную вещь.

И заодно — свой собственный изъян: функция `constraint_names()` брала
только check и unique, а пересечение дат брони это EXCLUDE. То есть самое
частое ограничение из всех в проверку не попадало. Список, который
спрашивают у базы, врёт ровно там, где неверен вопрос.

**Число, стоящее заголовком, никто не проверял.** «Ущерб до 15 000 ₸
решается автоматически» — заголовок на лендинге и у жюри, а сверки с
`app_settings.dispute_auto_threshold` не было. Хуже: всё, что `check:pitch`
сверял, сверялось с миграцией — с тем, что мы НАМЕРЕВАЛИСЬ положить в базу.
Обещание держит не намерение, а значение, лежащее там сейчас. Теперь
проверка спрашивает живую базу.

Мелочь на будущее: в вёрстке числа набраны неразрывным пробелом (U+00A0),
и `grep "15 000"` не находит ничего. Первая попытка измерить дала ноль
совпадений в обоих файлах — то есть выглядела как «числа вообще нет».

**Гипотеза, опровергнутая замером, экономит день.** Привязку Telegram сделал
один участник из пяти, и первым подозрением было техническое: Telegram
отдаёт номер без «плюса», бот ищет по «+7…», совпадения нет, привязка молча
не срабатывает. Гипотеза дорогая — если верна, менять надо код, а не текст.
Замер занял пять минут: все восемь номеров в базе в каноническом виде, а
`normalize_phone` в боте им и даёт. Гипотеза мертва, и строить баннеры уже
не жалко. Проверять надо было до, а не после.

**Число, ошибающееся в свою пользу, — самое опасное.** По дороге выяснилось,
что `npm run health` считал участниками всех верифицированных, включая два
тестовых аккаунта и витрину: «8 участников» при пяти живых, «Telegram
привязан 1 из 8» вместо «1 из 5». Ошибка выглядела мелкой ровно потому, что
льстила: пилот больше, чем есть. Этим числом меряют успех и называют его на
питче. Служебный диапазон теперь описан в `shared/service-accounts.json`.

**«Не могу» — это ещё не ответ, если можно сделать так, чтобы смогли оба.**
Настройку в панели агент нажать не может, и первым побуждением было
расписать человеку, что нажать. Правильный ответ оказался другим: сделать
инструмент, у которого проверка общая, а исполнителей двое. `npm run
auth` без ключей печатает, что нажать руками; с токеном аккаунта —
делает сам; проверяет одинаково в обоих случаях, потому что спрашивает
Supabase, а не того, кто нажимал. Инструкция, которую нельзя проверить,
превращается в спор «я же сделал» — а тут спорить не о чем.

Побочно это вскрыло третью копию адреса приложения: он был строкой в
`health`, в `invite` и собирался лечь в третий скрипт. Три копии расходятся
не «если», а «когда», и молча: каждая сама по себе верна. Теперь адрес один
— `shared/auth.json`, и `npm run auth` первым делом сверяет его с тем, что
просит `src/lib/supabase.ts`.

**Второе обещание нашлось через час после первого.** Функция `telegram-otp`
писала человеку «Действует час», а `sms_otp_exp` в проекте стоял 60 секунд.
Ни текст, ни настройка по отдельности не были ошибкой — врало их сочетание,
и узнал бы об этом человек, вернувшийся к коду через пять минут. Такие
расхождения чтением кода не ловятся: читать надо два места сразу, а они на
разных языках и в разных системах. Теперь срок 600 секунд, правда о нём в
`shared/auth.json`, а сверка — в `npm run auth`.

**Скриншот от человека стоит десяти замеров.** Диагноз «встроенный сервис
не доставляет письма» был построен на верных измерениях — 200 от API, 429
только со второго запроса — и оказался неверным. Опровергло его само
письмо: оно пришло. Когда цепочка длиннее вашего инструмента, спрашивайте
человека, что он видит, вместо ещё одного замера своей половины.

**Сравнение с NULL — не «ложь», а NULL, и `if` его пропускает.** Вся
находка дня выросла из одной строки, которую все читали как проверку:
`v_b.owner_id <> auth.uid()`. Она верна ровно до того момента, когда
`auth.uid()` пуст. Ищите такие сравнения везде, где рядом может оказаться
аноним, и помните, что глазами они выглядят правильными.

**Отказ, пришедший не оттуда, — не защита.** Первая попытка измерить дала
пять отказов из шести, и это была неправда: функции упирались в проверку
статуса, а не в проверку вызывающего. Меряйте каждую из того положения, в
котором она обязана срабатывать, — иначе меряется совпадение.

**Правило, написанное за двадцать минут до этого, ловит автора правила.**
Так было 03.09 с отзывом прав, так вышло и здесь: проверка «каждое
доступное анониму действие отказывает» уронила мою же заплатку — у
`booking_complete` она стояла под `if not p_force`, и вызов с
`p_force => null` шёл мимо. Та же трёхзначная логика, которая породила всю
находку.

**Тела функций не перепечатывают руками.** Миграция трогает восемь
функций; переписать девяносто строк SQL и не ошибиться в одной — задача,
которую нельзя проверить глазами. Тела извлечены скриптом из последних
миграций, где они определены, и отличаются ровно вставленной строкой.

**Кнопка, до которой нельзя дотянуться, ничем не лучше отсутствующей.**
В боте таблица действий раздавала семь кнопок, а показывала их карточка
«ваш ход» — и только если ход ваш. Три из семи не показывались никогда.
Сверяйте не только «что разрешено», но и «через что до этого дойти».

**«ok» от скрипта правки означает «в памяти», пока он не записал.**
Скрипты этой сессии копили замены и писали файл один раз в конце. Один упал
на последнем шаге — и два «ok», напечатанные до этого, отменились вместе с
ним. Потеря нашлась через сутки и не там, где случилась: перевод
ограничения просто отсутствовал в боте, хотя коммит на него ссылался.
Записывать после каждой замены и перечитывать обратно.

**Отказ, который приходит не оттуда, — не защита.** Повторю отдельно,
потому что ошибка повторилась дважды за день. Первый замер прав анонима
дал пять отказов из шести — и все пять пришли от проверки статуса. Первый
образец сверки списков нашёл `v_b.status not in (...)` в чужой функции.
Оба раза «похоже на нужное» означало «не то».

**`git checkout -- файл` откатывает и то, что вы не собирались.** Проверяя,
умеет ли новая сверка падать, я испортил файл нарочно, а вернул его
`git checkout` — вместе с четырьмя незакоммиченными правками того же файла.
Спасла копия, сделанная минутой раньше. Для таких проверок — копия и

## Чему научил вечер 03.09.2026

**Правило, применённое к одному полю из двух, — это не правило.** В
`bot.py` рядом стояли два комментария: «правила публикации бот не знает» и
«проверить здесь дешевле, чем показать отказ базы после шага с фото».
Второй был написан для ориентира и верен; первый оправдывал отсутствие
проверки названия. Оба выглядели как принцип, и ни один им не был. Ищите
такие пары внутри одного файла — не только между файлами.

**Заниженная цифра врёт так же, как завышенная.** «130+» на слайде было
правдой в день, когда его писали, и оставалось «не ложью» всё время, пока
устаревало. Разница только в том, что завышенную ловят на защите, а
заниженная просто отдаёт даром сильнейший аргумент. Цифру, которую печатает
инструмент, нельзя списывать в текст — надо записывать, откуда её брать.

**Непроверяемая цифра стоит столько же, сколько её отсутствие.** «345
автоматических проверок» жюри со слайда подтвердить не может, и звучит это
как «мы серьёзно относимся к качеству». Ссылка на папку в открытом
репозитории меняет жанр утверждения: из обещания в приглашение проверить.

**Демонстрационные данные становятся ложью в тот день, когда на них
приводят людей.** Восемь демо-объявлений были честными, пока витрину
смотрели свои. Лендинг с рекламой и страница для жюри превратили их в
обещание вещи, которую никто не отдаст, — и ни одна строчка кода при этом
не изменилась. Проверяйте не только код, но и то, кого мы теперь на него
приводим.

**`\n` не переживает heredoc, как и длинное тире.** HANDOFF предупреждал
про кириллицу; та же ловушка есть у обратных слэшей. Скрипт правки, где
якорь содержал `"...\n\n"`, молча не находил его: оболочка схлопнула
двойной слэш, и Python подставил настоящий перенос строки вместо двух
символов. Признак тот же — «якорь не найден» на строке, которая в файле
очевидно есть. Писать скрипт файлом, а не через stdin.

**Строки в бандле Expo экранированы, и поиск по ним даёт ноль на рабочем
коде.** `grep ДЕМО` по собранному бандлу нашёл ноль вхождений, хотя код
работал: Expo пишет кириллицу как `\uXXXX`. Искать надо в обеих формах —
или, что надёжнее, открыть страницу и посчитать в DOM.

## Чему научил 03.09.2026

**По умолчанию в Postgres открыто, а не закрыто, и путей два.** Новая
функция в `public` доступна анониму сразу: Postgres даёт `execute` роли
`PUBLIC`, Supabase сверх того выдаёт именной грант `anon` через `alter
default privileges`. Отзыв у `PUBLIC` не трогает второй, отзыв у `anon` не
трогает первый — **нужны обе строки**. Одна строка выглядит строже, а
закрывает меньше, и на этом попались семь миграций подряд.

**Отзыв прав, который не проверяется, не работает.** Правило «право
вызвать любую `bot_*` равно праву действовать от чужого имени» было
записано в `bot/README.md` словами с самого начала. Слова не мешают
скопировать не ту строку. Теперь правило проверяет стенд, и не списком
известных функций, а по признаку: параметр `p_actor` означает «действуем за
другого», значит сессионным ролям такая функция закрыта.

**Проверка «свой ли это вызов» по пустому `auth.uid()` неверна.** У
сервисного ключа он пуст, у планировщика пуст — и у `anon` тоже. Различать
надо роль: `current_setting('role', true)` переживает вход в `security
definer` и даёт `anon` / `authenticated` / `service_role` / `none`. Замерить
это стоило одной временной функции в стенде и десяти минут; гадать об этом
можно было бы час.

**Проверять надо и то, что запрет не переусердствовал.** Рядом с проверкой
«анониму отказано» стоит «сервисному ключу и планировщику разрешено». Без
второй «починка» безусловным запретом прошла бы стенд зелёной и сломала бы
бота с pg_cron на живой базе.

**Замер прежде диагноза — снова.** Все двенадцать путей сначала измерялись
временными `raise notice` в стенде и только потом чинились. Два
предположения из двенадцати оказались неверны: `moderation_people` и
`set_user_blocked` были закрыты правильно, хотя выглядели такими же. Список,
составленный чтением кода, включил бы их и утопил бы настоящие находки в
шуме.

**Собственная заплатка не закрыла дыру, и это поймал стенд.** Первая
версия отзывала права только у `anon` — и пять функций остались открыты
через `PUBLIC`. Правило, написанное за двадцать минут до этого, поймало
ошибку автора правила через один прогон.

## Чему научил 02.09.2026

**Проверять правку в приложении переходом на тот же путь нельзя.**
expo-router обрабатывает такой переход внутри приложения, не обращаясь к
серверу: в памяти остаётся бандл, загруженный при первом открытии вкладки.
Три подряд «неудачные» проверки прокрутки ряда категорий были проверками
кода недельной давности — настолько старого, что его файл на Pages уже
отдавал 404, пока страница на нём работала.

Признак подмены: имя бандла в DOM не совпадает с тем, что отдаёт `curl`.

```bash
curl -s https://mandaloriancs.github.io/renthub/app/ | grep -o 'entry-[a-f0-9]*\.js'
```

Проверять — полной перезагрузкой: сначала уйти на другой адрес (например
на лендинг), потом вернуться.

**Живой сайт собирает GitHub Actions, а не наш `docs/`.** Хеши бандла на
Pages не совпадают ни с одной локальной сборкой, потому что Actions
собирает приложение сам, из того же исходника, но своим окружением.
Одновременно старый путь Jekyll публикует закоммиченный `docs/`. Кто
победит — решает гонка; содержимое при этом одинаковое, потому что
исходник один. Убрать неопределённость может только владелец репозитория:
Settings → Pages → Source: GitHub Actions.

**`set_config(..., true)` не откатывается при выходе из функции.**
«Локальный» здесь означает транзакцию, а не функцию, — вопреки разбору в
`20260828100000_bot_acts_as_user.sql`. Флаг `renthub.system_write`,
поставленный функцией модератора, оставался включённым до конца
транзакции и открывал дорогу мимо сторожей. Измерено на стенде, исправлено
в `20260902090000_system_write_scope.sql`: флаг гасится сразу после
защищённой записи.

**Скрипты с кириллицей нельзя передавать в `python -` через heredoc.**
Замены молча не находят якорь: длинное тире и часть символов не переживают
перекодировку stdin. Писать скрипт в файл и запускать файлом.

**Локальный сервер в `docs/` ломает `npm run build:pages`.** Сборка
удаляет папку и падает с `EPERM`, а вывод про «Живые адреса» при этом не
появляется — легко принять за успех. Поднимать сервер из корня или гасить
перед сборкой.

## Чему научил 31.08.2026

Стенд поймал два дефекта, каждый из которых уже был на живой базе.

**Блокировка падала на собственном запрете.** `set_user_blocked()` сначала
ставила `blocked_at`, потом снимала объявления. Между шагами стоит триггер
`items_verify_owner` — он зовёт `assert_verified()`, а тот проверяет
`blocked_at`. Функция упиралась в собственный запрет и падала с
`RENTHUB_BLOCKED`. Ломалась ровно тогда, когда нужна: у нарушителя есть
активные объявления. Без них `update` не задевал строк, триггер не
срабатывал, и ручная проверка на живой базе ничего не заметила. Починено
миграцией `20260831100000_block_order`: объявления снимаются ДО отметки.

**Дыра, помеченная в README как закрытая, была открыта.** 28.08 отмена
переехала в `booking_cancel()`, и вопрос закрыли — а политика
`bookings_cancel_pending` осталась, и с ней прямой `update bookings set
status = 'cancelled', renter_total = 1`. Добавить дверь — не то же самое,
что закрыть старую. Починено `20260831110000_lock_cancel_amounts`: политика
удалена, у `authenticated` не осталось ни одной UPDATE-политики на
`bookings`.

Три ловушки, которые стоит помнить при следующей миграции:

- **`create or replace` не меняет тип результата.** Добавили колонку в
  `returns table` — пишите `drop function` перед `create` и выдавайте
  гранты заново: дроп снимает их вместе с функцией.
- **RLS фильтрует строки, а не отклоняет запрос.** `expect_fail` на чужой
  строке никогда не сработает: запрос пройдёт, изменив ноль строк.
  Проверять надо результат, а не исключение. Этим же объясняется, почему
  после удаления политики пришлось править уборку в конце сценария 2:
  прямой `update` там молча менял ноль строк, а падало это через два
  сценария конфликтом `bookings_no_overlap`.
- **Проверка, которая не может упасть, хуже отсутствующей.** За две сессии
  их нашлось три: тест на `item_cheap`, который заводится только в сценарии
  4; `count(*) >= 0`; и проверка «суммы при отмене не меняются» через
  функцию, которая сумм и не трогает. Каждая занимала место настоящей и
  создавала впечатление, что та есть.

> находки этих суток — свой список статусов против таблицы «чей ход», две
> копии проверки модератора, счётчик фильтров против пустого экрана,
> подсказки на латинице против поиска на кириллице, адрес бота строкой
> против того же адреса переменной. Сверка занимает двадцать минут и
> находит то, чего не видно глазами.
>
> Самая дорогая находка 03.09 пришла из соседней разновидности того же
> приёма: **сверять объявленное правило с тем, что его действительно
> держит.** `bot/README.md` с самого начала писал, что право вызвать любую
> `bot_*` равно праву действовать от чужого имени, — а в пяти обёртках
> `revoke` стоял не для той роли. Правило жило в документации, а не в
> базе. Ищите такие пары: что обещано словами против того, что проверено
> кодом или стендом.
>
> И измеряйте, прежде чем чинить. Двенадцать открытых путей сначала
> измерялись временными `raise notice` в стенде: два предположения из
> двенадцати оказались неверны, и список, составленный чтением кода,
> утопил бы настоящие находки в шуме. Собственную заплатку тоже измеряйте
> — первая версия не закрыла пять функций, и поймал это стенд, а не
> перечитывание.
>
> Второй продуктивный приём — спрашивать «что увидит человек, если». Если
> сеть отвалится. Если он напишет боту незнакомый текст. Если у него нет
> приглашения. Если фильтр не дал результатов. Молчание в ответ на действие
> человек читает как поломку, и уходит.
>
> И держи в уме, что инструмент врёт чаще кода: панель браузера не
> перезагружает SPA и показывает бандл недельной давности, скриншот
> кадрирует то, что в DOM помещается, а `IntersectionObserver` не успевает
> за программной прокруткой. Прежде чем чинить «дефект», найденный глазами,
> измерь его.
