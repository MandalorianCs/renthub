## Как здесь всё устроено

**Бизнес-правила живут в Postgres**, а не в React: позже подключится
Telegram-бот, и правило в компоненте он обойдёт. Переходы статусов — только
через RPC, суммы проставляет триггер из цены объявления, пороги в
`app_settings`.

**Схема разворачивается пушем в `main`** — подключена GitHub-интеграция
Supabase. Отсюда правило: **не менять схему через SQL Editor**, иначе
следующий деплой падает с ошибкой синхронизации.

**Перед каждым пушем прогонять стенд.** Он поднимает чистый Postgres в
Docker, накатывает миграции и проезжает четыре сценария с включённым RLS:

```
npm run test:db
```

**Сайт собирается при пуше** — GitHub Actions (`.github/workflows/pages.yml`)
запускает `npm run build:pages` и публикует результат. Отдельно коммитить
`docs/` больше не нужно: сайт всегда собран из того кода, что лежит в `main`.
Папка `docs/` **снова в репозитории** — вынужденно. Пока в настройках
стоит Source = «Deploy from a branch → /docs», GitHub при каждом пуше лезет
за ней в ветку и без неё падает на шаге «Build with Jekyll». Красным, на
каждом пуше.

**Пока папка в репозитории, её надо держать свежей.** Правка фронта —
значит `npm run build:pages` и `git add docs/` тем же коммитом. Иначе
повторится то, из-за чего её и убирали: публикуют два процесса сразу, и
на адресе оказывается тот, кто финишировал вторым, — то есть иногда
старая сборка поверх свежей.

**Осталось переключить настройку Pages — это не косметика.** До 01.09.2026
сайт публиковали ДВА процесса сразу: наш workflow (свежая сборка из кода) и
встроенный «pages build and deployment», который брал папку `docs/` прямо
из ветки. У обоих `deploy` завершался успехом, и на адресе оказывался тот,
кто финишировал вторым, — а `docs/` в ветке отставала. Отсюда и случаи,
когда «код запушили, а на сайте старое».

Сейчас гонки нет: без папки встроенный workflow падает на шаге
«Build with Jekyll» и ничего не публикует, остаётся один источник. Но
падать он будет при каждом пуше и светиться красным в Actions, а красный
статус, который «так и должно быть», рано или поздно скроет настоящую
поломку.

Чинится один раз, в веб-интерфейсе: **Settings → Pages → Build and
deployment → Source: GitHub Actions**. После этого встроенный workflow
перестанет запускаться совсем. Агент этого сделать не может — нужен доступ
к настройкам репозитория.

Та же команда локально даёт предпросмотр в `docs/` — посмотреть до пуша
полезно, но публикацию она не делает.

**Локальная работа и публичный адрес — один проект.** Продукт смотрят по
ссылке `https://mandaloriancs.github.io/renthub/app/`, а не на чьём-то
dev-сервере: работа, оставшаяся в рабочем дереве, для пилота не
существует. Отсюда три следствия:

- доводить сделанное до пуша в `main`, а не оставлять локально
  (исключение одно — миграция без зелёного стенда, см. правило заморозки
  ниже);
- ссылки давать публичные, не `localhost:8081`;
- держать `.env` и дефолты в `.github/workflows/pages.yml` одинаковыми.
  Разойдутся — локальная сборка перестанет соответствовать опубликованной,
  причём молча. Проверено 31.08.2026: `EXPO_PUBLIC_TELEGRAM_BOT` была
  только в CI, локально работал дефолт из `src/lib/supabase.ts`.

Проверить, что правки реально доехали, можно по бандлу — строки в нём
экранированы, искать надо в обеих формах:

```bash
curl -s https://mandaloriancs.github.io/renthub/app/ | grep -o '_expo/static/js/web/[^"]*\.js'
```

```
npm run demo:photos                 заглушки для витрины, если фото нет

npm run demo:fill                   демо-объявления из demo-photos/

npm run notify:clear                убрать проверочные уведомления
npm run bot                         бот в Telegram (отдельное окно, свой .env)
                                    /start /deals /каталог /найти /сдать
                                    /вещи /профиль /поддержка /help
                                    /отмена /unlink
```

Всё, что ходит в базу мимо RLS, требует секретного ключа — от `seed:users`
и `whoami` до `bot`. Считать их по порядку в списке не надо: признак в том,
что команда читает или пишет чужие строки. Ключ лежит в `.env.secret` —
файл в `.gitignore`, сборка Expo его не читает:

```
SUPABASE_SECRET_KEY=sb_secret_...
```

Разово перебивается переменной окружения:

```
$env:SUPABASE_SECRET_KEY="sb_secret_..."; npm run invite -- +7701... "Имя"
```

Сборка в облаке не видит `.env` — он в `.gitignore`, а EAS забирает проект по
git. Переменные лежат в окружениях EAS, профили в `eas.json` ссылаются на них
полем `environment`. Один раз выложить и проверить:

```
eas env:push preview --path .env --force
eas env:list preview
```

## Чего агент делать не должен

- **Не печатать `sb_secret_` и не писать его в репозиторий.** Сам ключ лежит
  в `.env.secret`, скрипты читают его оттуда — значит запускать `invite`,
  `moderator`, `demo:fill` и `notify:test` агент может сам, не видя значения.
  Запрет с 21.08.2026 касается только разглашения: не выводить в консоль,
  не коммитить, не пересылать.
- **Коммитить и пушить агент может сам** (разрешено 21.08.2026), но перед
  пушем миграций обязателен `npm run test:db`: пуш применяет схему к живой
  базе, и отменить это одним нажатием нельзя.
- **Пока миграция ждёт стенда — ветка заморожена.** `git push` отправляет
  ветку целиком, а не последний коммит. Коммит поверх непроверенной
  миграции и невинный пуш уносят в живую базу обоих. Проверено на себе
  28.08.2026: уехала непроверенная `20260828120000_block_hides_items`.
  Правильно — держать такую миграцию в отдельной ветке
  (`git switch -c migration/имя`) и вливать её в `main` после зелёного
  стенда. Тогда работа в `main` не блокируется сломанным Docker.
- **Не писать телефоны и ключи в репозиторий** — он публичный.
- **Не менять схему через SQL Editor** — только новой миграцией и пушем.
- **Не ставить UI-киты** (Tamagui, gluestack, Material): они принесут свой
  визуальный язык вместо бренда из деки. Из открытого кода берём поведение
  и ресурсы, не внешний вид.

## Особенности окружения

- Терминал часто открывается в папке выше — перед npm-командами `cd` в
  `renthub`.
- Docker Desktop падает из-за компонента Docker AI (Inference manager) —
  повторяется регулярно. `EnableDockerAI` в настройках стоит `false`, но
  менеджер всё равно стартует и спотыкается об остаток сокета
  `%LOCALAPPDATA%\Docker\run\dockerInference`: Windows отвечает «файл
  недоступен системе» и не даёт его удалить ни обычным путём, ни через
  `\\?\`, ни после `wsl --shutdown`.

  **Причина найдена 31.08.2026.** `dockerInference` — не обычный файл, а
  AF_UNIX-сокет; в Windows это reparse point (атрибут `ReparsePoint`,
  режим `-a---l`, размер 0). После аварийного завершения объект остаётся,
  и держит его драйвер ядра `afunix.sys`, а не процесс. Поэтому его не
  берёт ничто: ни `Remove-Item`, ни `\\?\`, ни `fsutil reparsepoint
  delete` — все получают ошибку 1920 (`ERROR_CANT_ACCESS_FILE`). Папка при
  этом исправна: обычный файл в ней создаётся и удаляется.

  **Обход, который работает без перезагрузки.** Застрявших сокетов больше
  одного, и Docker падает на них по очереди: уберёте первый — упрётся во
  второй. Убирать надо обе папки сразу:

  ```
  %LOCALAPPDATA%\Docker\run
  %LOCALAPPDATA%\docker-secrets-engine
  ```

  Порядок: закрыть процессы Docker, переименовать обе папки (Docker создаст
  новые), запустить Docker Desktop. Проверено 31.08.2026 — движок поднялся
  без перезагрузки, стенд прошёл.

  Точную причину падения показывает лог, а не диалог:
  `%LOCALAPPDATA%\Docker\log\host\com.docker.backend.exe.log`, искать
  `backend crashed`. Именно так выяснилось, что после первой папки Docker
  начал падать уже на Secrets Engine.

  Кнопку **Reset to factory defaults** в диалоге не нажимать: она сотрёт
  образы и контейнеры, а причина не в них.

  Без Docker не работает `npm run test:db`, а значит нельзя пушить
  миграции — правило «сначала стенд» держится именно на нём.
- SMS-провайдер не подключён и не нужен: для Казахстана Twilio требует
  $250/мес только за регистрацию имени отправителя, а Telegram даёт более
  сильное подтверждение бесплатно. В `.env` и в дефолтах `pages.yml` стоит
  `EXPO_PUBLIC_AUTH_MODE=sms` — код приходит в Telegram через
  `telegram-otp`, а не эсэмэской. Дефолт в коде (`app/sign-in.tsx`) и в
  `.env.example` остался `invite`: без переменной приложение открывается на
  вкладке приглашений, и это правильно для того, кто клонировал репозиторий
  и ещё ничего не развернул.
- **Бот не поднимается сам.** Он живёт отдельным процессом, и после
  перезагрузки компьютера его надо запустить руками: `npm run bot`.
  Симптом, если забыть, — `/start` не отвечает, а уведомления копятся в
  базе с пустым `sent_at` и приходят пачкой после запуска. Проверить, жив
  ли он: в логе при старте должно быть `Run polling for bot @…`.
- Бот работает отдельным процессом и держит секретный ключ: `bot/.env`
  (только токен Telegram) плюс корневые `.env` и `.env.secret`. Пока окно с
  ботом закрыто, уведомления копятся в базе и придут после запуска.

## Ограничение хостинга, о котором надо знать

**Ссылки на карточки объявлений отдают HTTP 404.** Проверить:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://mandaloriancs.github.io/renthub/app/item/64a6fde6-1fcd-4d8c-bb41-059dc2086620
```

Для человека всё открывается: GitHub Pages отдаёт `docs/404.html`, внутри
которого лежит приложение, и expo-router разбирает адрес сам. Но статус
остаётся ошибкой, и это не чинится кодом: статический хостинг не умеет
отвечать 200 на маршруты, которых нет файлами.

Чем это платится сегодня: поисковики не индексируют страницы объявлений.
На пилоте из одного города это не тот канал, которым он растёт, — растёт
он лендингом и пересылкой ссылок, а превью в мессенджере работает,
og-теги в `404.html` вставляет `build-pages.mjs`.

Чем это станет платиться, когда объявлений будут сотни: витрина не
попадёт в поиск целиком. Лечится переездом на хостинг с переписыванием
адресов — Vercel, Netlify, Cloudflare Pages: там правило «всё, что не
файл, отдавать index приложения со статусом 200» настраивается одной
строкой. Менять код при этом не придётся.

## Чему научил 03.09.2026

**По умолчанию в Postgres открыто, а не закрыто, и путей два.** Новая
функция в `public` доступна анониму сразу: Postgres даёт `execute` роли
`PUBLIC`, Supabase сверх того выдаёт именной грант `anon` через `alter
default privileges`. Отзыв у `PUBLIC` не трогает второй, отзыв у `anon` не
трогает первый — **нужны обе строки**. Одна строка выглядит строже, а
закрывает меньше, и на этом попались семь миграций подряд.

**Отзыв прав, который не проверяется, не работает.** Правило «право
вызвать любую `bot_*` равно праву действовать от чужого имени» было
записано в `bot/README.md` словами с самого начала. Слова не мешают
скопировать не ту строку. Теперь правило проверяет стенд, и не списком
известных функций, а по признаку: параметр `p_actor` означает «действуем за
другого», значит сессионным ролям такая функция закрыта.

**Проверка «свой ли это вызов» по пустому `auth.uid()` неверна.** У
сервисного ключа он пуст, у планировщика пуст — и у `anon` тоже. Различать
надо роль: `current_setting('role', true)` переживает вход в `security
definer` и даёт `anon` / `authenticated` / `service_role` / `none`. Замерить
это стоило одной временной функции в стенде и десяти минут; гадать об этом
можно было бы час.

**Проверять надо и то, что запрет не переусердствовал.** Рядом с проверкой
«анониму отказано» стоит «сервисному ключу и планировщику разрешено». Без
второй «починка» безусловным запретом прошла бы стенд зелёной и сломала бы
бота с pg_cron на живой базе.

**Замер прежде диагноза — снова.** Все двенадцать путей сначала измерялись
временными `raise notice` в стенде и только потом чинились. Два
предположения из двенадцати оказались неверны: `moderation_people` и
`set_user_blocked` были закрыты правильно, хотя выглядели такими же. Список,
составленный чтением кода, включил бы их и утопил бы настоящие находки в
шуме.

**Собственная заплатка не закрыла дыру, и это поймал стенд.** Первая
версия отзывала права только у `anon` — и пять функций остались открыты
через `PUBLIC`. Правило, написанное за двадцать минут до этого, поймало
ошибку автора правила через один прогон.

## Чему научил 02.09.2026

**Проверять правку в приложении переходом на тот же путь нельзя.**
expo-router обрабатывает такой переход внутри приложения, не обращаясь к
серверу: в памяти остаётся бандл, загруженный при первом открытии вкладки.
Три подряд «неудачные» проверки прокрутки ряда категорий были проверками
кода недельной давности — настолько старого, что его файл на Pages уже
отдавал 404, пока страница на нём работала.

Признак подмены: имя бандла в DOM не совпадает с тем, что отдаёт `curl`.

```bash
curl -s https://mandaloriancs.github.io/renthub/app/ | grep -o 'entry-[a-f0-9]*\.js'
```

Проверять — полной перезагрузкой: сначала уйти на другой адрес (например
на лендинг), потом вернуться.

**Живой сайт собирает GitHub Actions, а не наш `docs/`.** Хеши бандла на
Pages не совпадают ни с одной локальной сборкой, потому что Actions
собирает приложение сам, из того же исходника, но своим окружением.
Одновременно старый путь Jekyll публикует закоммиченный `docs/`. Кто
победит — решает гонка; содержимое при этом одинаковое, потому что
исходник один. Убрать неопределённость может только владелец репозитория:
Settings → Pages → Source: GitHub Actions.

**`set_config(..., true)` не откатывается при выходе из функции.**
«Локальный» здесь означает транзакцию, а не функцию, — вопреки разбору в
`20260828100000_bot_acts_as_user.sql`. Флаг `renthub.system_write`,
поставленный функцией модератора, оставался включённым до конца
транзакции и открывал дорогу мимо сторожей. Измерено на стенде, исправлено
в `20260902090000_system_write_scope.sql`: флаг гасится сразу после
защищённой записи.

**Скрипты с кириллицей нельзя передавать в `python -` через heredoc.**
Замены молча не находят якорь: длинное тире и часть символов не переживают
перекодировку stdin. Писать скрипт в файл и запускать файлом.

**Локальный сервер в `docs/` ломает `npm run build:pages`.** Сборка
удаляет папку и падает с `EPERM`, а вывод про «Живые адреса» при этом не
появляется — легко принять за успех. Поднимать сервер из корня или гасить
перед сборкой.

## Чему научил 31.08.2026

Стенд поймал два дефекта, каждый из которых уже был на живой базе.

**Блокировка падала на собственном запрете.** `set_user_blocked()` сначала
ставила `blocked_at`, потом снимала объявления. Между шагами стоит триггер
`items_verify_owner` — он зовёт `assert_verified()`, а тот проверяет
`blocked_at`. Функция упиралась в собственный запрет и падала с
`RENTHUB_BLOCKED`. Ломалась ровно тогда, когда нужна: у нарушителя есть
активные объявления. Без них `update` не задевал строк, триггер не
срабатывал, и ручная проверка на живой базе ничего не заметила. Починено
миграцией `20260831100000_block_order`: объявления снимаются ДО отметки.

**Дыра, помеченная в README как закрытая, была открыта.** 28.08 отмена
переехала в `booking_cancel()`, и вопрос закрыли — а политика
`bookings_cancel_pending` осталась, и с ней прямой `update bookings set
status = 'cancelled', renter_total = 1`. Добавить дверь — не то же самое,
что закрыть старую. Починено `20260831110000_lock_cancel_amounts`: политика
удалена, у `authenticated` не осталось ни одной UPDATE-политики на
`bookings`.

Три ловушки, которые стоит помнить при следующей миграции:

- **`create or replace` не меняет тип результата.** Добавили колонку в
  `returns table` — пишите `drop function` перед `create` и выдавайте
  гранты заново: дроп снимает их вместе с функцией.
- **RLS фильтрует строки, а не отклоняет запрос.** `expect_fail` на чужой
  строке никогда не сработает: запрос пройдёт, изменив ноль строк.
  Проверять надо результат, а не исключение. Этим же объясняется, почему
  после удаления политики пришлось править уборку в конце сценария 2:
  прямой `update` там молча менял ноль строк, а падало это через два
  сценария конфликтом `bookings_no_overlap`.
- **Проверка, которая не может упасть, хуже отсутствующей.** За две сессии
  их нашлось три: тест на `item_cheap`, который заводится только в сценарии
  4; `count(*) >= 0`; и проверка «суммы при отмене не меняются» через
  функцию, которая сумм и не трогает. Каждая занимала место настоящей и
  создавала впечатление, что та есть.

> приглашения. Если фильтр не дал результатов. Молчание в ответ на действие
> человек читает как поломку, и уходит.
>
> И держи в уме, что инструмент врёт чаще кода: панель браузера не
> перезагружает SPA и показывает бандл недельной давности, скриншот
> кадрирует то, что в DOM помещается, а `IntersectionObserver` не успевает
> за программной прокруткой. Прежде чем чинить «дефект», найденный глазами,
> измерь его.
