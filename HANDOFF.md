## Как здесь всё устроено

**Бизнес-правила живут в Postgres**, а не в React: позже подключится
Telegram-бот, и правило в компоненте он обойдёт. Переходы статусов — только
через RPC, суммы проставляет триггер из цены объявления, пороги в
`app_settings`.

**Схема разворачивается пушем в `main`** — подключена GitHub-интеграция
Supabase. Отсюда правило: **не менять схему через SQL Editor**, иначе
следующий деплой падает с ошибкой синхронизации.

**Перед каждым пушем прогонять стенд.** Он поднимает чистый Postgres в
Docker, накатывает миграции и проезжает четыре сценария с включённым RLS:

```
npm run test:db
```

**Сайт собирается при пуше** — GitHub Actions (`.github/workflows/pages.yml`)
запускает `npm run build:pages` и публикует результат. Отдельно коммитить
`docs/` больше не нужно: сайт всегда собран из того кода, что лежит в `main`.
С 01.09.2026 папки нет и в репозитории — она производное, и лежавшая там
сборка успела отстать от кода, показывая старую версию рядом со свежими
исходниками.

Та же команда локально даёт предпросмотр в `docs/` — посмотреть до пуша
полезно, но публикацию она не делает.

**Локальная работа и публичный адрес — один проект.** Продукт смотрят по
ссылке `https://mandaloriancs.github.io/renthub/app/`, а не на чьём-то
dev-сервере: работа, оставшаяся в рабочем дереве, для пилота не
существует. Отсюда три следствия:

- доводить сделанное до пуша в `main`, а не оставлять локально
  (исключение одно — миграция без зелёного стенда, см. правило заморозки
  ниже);
- ссылки давать публичные, не `localhost:8081`;
- держать `.env` и дефолты в `.github/workflows/pages.yml` одинаковыми.
  Разойдутся — локальная сборка перестанет соответствовать опубликованной,
  причём молча. Проверено 31.08.2026: `EXPO_PUBLIC_TELEGRAM_BOT` была
  только в CI, локально работал дефолт из `src/lib/supabase.ts`.

Проверить, что правки реально доехали, можно по бандлу — строки в нём
экранированы, искать надо в обеих формах:

```bash
curl -s https://mandaloriancs.github.io/renthub/app/ | grep -o '_expo/static/js/web/[^"]*\.js'
```

## Рабочие команды

```
npm run web             локальный сервер
npm run test:db         стенд миграций (нужен Docker)
npm run typecheck       tsc
npm run build:pages     пересобрать публикацию
npm run apk             сборка APK в облаке EAS (нужен eas login)
npm run update          правки по воздуху в уже установленные APK
npm run invite -- +7701... "Имя"    завести участника, выдать пароль
npm run invite -- +7701... "Имя" a@mail.com   то же плюс вход по почте
npm run moderator -- +7701...       право разбирать споры
npm run demo:fill                   демо-объявления из demo-photos/
npm run demo:clear                  убрать их
npm run notify:test -- +7701...     проверить связь «база → бот → Telegram»
npm run notify:clear                убрать проверочные уведомления
python bot/bot.py                   бот в Telegram (отдельное окно, свой .env)
                                    /start /deals /каталог /найти /сдать
                                    /help /отмена /unlink
```

Последние четыре требуют секретного ключа. Он лежит в `.env.secret` — файл
в `.gitignore`, сборка Expo его не читает:

```
SUPABASE_SECRET_KEY=sb_secret_...
```

Разово перебивается переменной окружения:

```
$env:SUPABASE_SECRET_KEY="sb_secret_..."; npm run invite -- +7701... "Имя"
```

Сборка в облаке не видит `.env` — он в `.gitignore`, а EAS забирает проект по
git. Переменные лежат в окружениях EAS, профили в `eas.json` ссылаются на них
полем `environment`. Один раз выложить и проверить:

```
eas env:push preview --path .env --force
eas env:list preview
```

## Чего агент делать не должен

- **Не печатать `sb_secret_` и не писать его в репозиторий.** Сам ключ лежит
  в `.env.secret`, скрипты читают его оттуда — значит запускать `invite`,
  `moderator`, `demo:fill` и `notify:test` агент может сам, не видя значения.
  Запрет с 21.08.2026 касается только разглашения: не выводить в консоль,
  не коммитить, не пересылать.
- **Коммитить и пушить агент может сам** (разрешено 21.08.2026), но перед
  пушем миграций обязателен `npm run test:db`: пуш применяет схему к живой
  базе, и отменить это одним нажатием нельзя.
- **Пока миграция ждёт стенда — ветка заморожена.** `git push` отправляет
  ветку целиком, а не последний коммит. Коммит поверх непроверенной
  миграции и невинный пуш уносят в живую базу обоих. Проверено на себе
  28.08.2026: уехала непроверенная `20260828120000_block_hides_items`.
  Правильно — держать такую миграцию в отдельной ветке
  (`git switch -c migration/имя`) и вливать её в `main` после зелёного
  стенда. Тогда работа в `main` не блокируется сломанным Docker.
- **Не писать телефоны и ключи в репозиторий** — он публичный.
- **Не менять схему через SQL Editor** — только новой миграцией и пушем.
- **Не ставить UI-киты** (Tamagui, gluestack, Material): они принесут свой
  визуальный язык вместо бренда из деки. Из открытого кода берём поведение
  и ресурсы, не внешний вид.

## Особенности окружения

- Терминал часто открывается в папке выше — перед npm-командами `cd` в
  `renthub`.
- Docker Desktop падает из-за компонента Docker AI (Inference manager) —
  повторяется регулярно. `EnableDockerAI` в настройках стоит `false`, но
  менеджер всё равно стартует и спотыкается об остаток сокета
  `%LOCALAPPDATA%\Docker\run\dockerInference`: Windows отвечает «файл
  недоступен системе» и не даёт его удалить ни обычным путём, ни через
  `\\?\`, ни после `wsl --shutdown`.

  **Причина найдена 31.08.2026.** `dockerInference` — не обычный файл, а
  AF_UNIX-сокет; в Windows это reparse point (атрибут `ReparsePoint`,
  режим `-a---l`, размер 0). После аварийного завершения объект остаётся,
  и держит его драйвер ядра `afunix.sys`, а не процесс. Поэтому его не
  берёт ничто: ни `Remove-Item`, ни `\\?\`, ни `fsutil reparsepoint
  delete` — все получают ошибку 1920 (`ERROR_CANT_ACCESS_FILE`). Папка при
  этом исправна: обычный файл в ней создаётся и удаляется.

  **Обход, который работает без перезагрузки.** Застрявших сокетов больше
  одного, и Docker падает на них по очереди: уберёте первый — упрётся во
  второй. Убирать надо обе папки сразу:

  ```
  %LOCALAPPDATA%\Docker\run
  %LOCALAPPDATA%\docker-secrets-engine
  ```

  Порядок: закрыть процессы Docker, переименовать обе папки (Docker создаст
  новые), запустить Docker Desktop. Проверено 31.08.2026 — движок поднялся
  без перезагрузки, стенд прошёл.

  Точную причину падения показывает лог, а не диалог:
  `%LOCALAPPDATA%\Docker\log\host\com.docker.backend.exe.log`, искать
  `backend crashed`. Именно так выяснилось, что после первой папки Docker
  начал падать уже на Secrets Engine.

  Кнопку **Reset to factory defaults** в диалоге не нажимать: она сотрёт
  образы и контейнеры, а причина не в них.

  Без Docker не работает `npm run test:db`, а значит нельзя пушить
  миграции — правило «сначала стенд» держится именно на нём.
- SMS-провайдер не подключён и не нужен: для Казахстана Twilio требует
  $250/мес только за регистрацию имени отправителя, а Telegram даёт более
  сильное подтверждение бесплатно. Сейчас вход по приглашениям,
  `EXPO_PUBLIC_AUTH_MODE=invite`; вкладка «По SMS» включится сменой
  переменной, когда будет развёрнута функция `telegram-otp`.
- Бот работает отдельным процессом и держит секретный ключ: `bot/.env`
  (только токен Telegram) плюс корневые `.env` и `.env.secret`. Пока окно с
  ботом закрыто, уведомления копятся в базе и придут после запуска.

## Чему научил 31.08.2026

Стенд поймал два дефекта, каждый из которых уже был на живой базе.

**Блокировка падала на собственном запрете.** `set_user_blocked()` сначала
ставила `blocked_at`, потом снимала объявления. Между шагами стоит триггер
`items_verify_owner` — он зовёт `assert_verified()`, а тот проверяет
`blocked_at`. Функция упиралась в собственный запрет и падала с
`RENTHUB_BLOCKED`. Ломалась ровно тогда, когда нужна: у нарушителя есть
активные объявления. Без них `update` не задевал строк, триггер не
срабатывал, и ручная проверка на живой базе ничего не заметила. Починено
миграцией `20260831100000_block_order`: объявления снимаются ДО отметки.

**Дыра, помеченная в README как закрытая, была открыта.** 28.08 отмена
переехала в `booking_cancel()`, и вопрос закрыли — а политика
`bookings_cancel_pending` осталась, и с ней прямой `update bookings set
status = 'cancelled', renter_total = 1`. Добавить дверь — не то же самое,
что закрыть старую. Починено `20260831110000_lock_cancel_amounts`: политика
удалена, у `authenticated` не осталось ни одной UPDATE-политики на
`bookings`.

Три ловушки, которые стоит помнить при следующей миграции:

- **`create or replace` не меняет тип результата.** Добавили колонку в
  `returns table` — пишите `drop function` перед `create` и выдавайте
  гранты заново: дроп снимает их вместе с функцией.
- **RLS фильтрует строки, а не отклоняет запрос.** `expect_fail` на чужой
  строке никогда не сработает: запрос пройдёт, изменив ноль строк.
  Проверять надо результат, а не исключение. Этим же объясняется, почему
  после удаления политики пришлось править уборку в конце сценария 2:
  прямой `update` там молча менял ноль строк, а падало это через два
  сценария конфликтом `bookings_no_overlap`.
- **Проверка, которая не может упасть, хуже отсутствующей.** За две сессии
  их нашлось три: тест на `item_cheap`, который заводится только в сценарии
  4; `count(*) >= 0`; и проверка «суммы при отмене не меняются» через
  функцию, которая сумм и не трогает. Каждая занимала место настоящей и
  создавала впечатление, что та есть.
