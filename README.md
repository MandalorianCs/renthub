# RentHUB

P2P-аренда вещей, Казахстан. Пилот — узкая ниша: строительная техника и инструмент,
один город.

**Этап: MVP без реальных платежей.** Бронирования, депозиты и выплаты полностью
живут в базе как статусы, но деньги не двигаются. Смысл этапа — проверить, что
работает петля «выложил → нашли → забронировали → вернули», а не гладкость
платежей. Kaspi Pay / CloudPayments подключаются отдельным этапом, когда петля
подтверждена живыми людьми.

## Стек

| Слой | Технология |
|---|---|
| Клиент | Expo (React Native + TypeScript) — один код на iOS, Android и веб |
| Навигация | expo-router (файловая маршрутизация) |
| Бэкенд | Supabase: Postgres + Auth (SMS-код) + Storage для фото |
| Позже | Telegram-бот на aiogram — подключается к этой же базе |

Бэкенд один. Приложение и будущий бот — два разных «окна» в него, а не два
отдельных проекта.

## Запуск

```bash
npm install
```

1. Создайте проект на [supabase.com](https://supabase.com). При создании
   **оставьте включённой** галочку «Automatically expose new tables»: в
   миграциях нет ни одного `grant`, доступ разграничен политиками RLS. Без
   неё приложение получит `permission denied for table items` при верных
   политиках.
2. Схема приезжает пушем — см. «Миграции и деплой» ниже.
3. Включите вход по телефону: **Authentication → Providers → Phone**, подключите
   SMS-провайдера (Twilio / Vonage / MessageBird).
4. Скопируйте `.env.example` в `.env` и подставьте URL и anon-ключ из
   **Project Settings → API**. Переменные `EXPO_PUBLIC_` вшиваются в бандл при
   сборке, поэтому после правки `.env` сервер надо перезапустить — на живом
   он подхватит только старые значения.

```bash
npm run web      # веб-версия в браузере
npm start        # QR-код для Expo Go на телефоне
```

## Миграции и деплой

Схема живёт в `supabase/migrations/` и приезжает на проект **пушем в `main`**:
подключена GitHub-интеграция Supabase, она сверяет папку с таблицей
`supabase_migrations.schema_migrations` и выполняет только новое.

Отсюда одно правило, нарушать которое дорого:

> **Не менять схему через SQL Editor.** Правки мимо миграций не попадают в
> учёт, и следующий деплой падает с ошибкой синхронизации. Любое изменение —
> новый файл в `supabase/migrations/`, проверенный локально и отправленный
> пушем.

Имена файлов — временные метки (`20260816120000_schema.sql`), этого требует
Supabase CLI: по ним определяется порядок и ведётся история.

## Проверка миграций

```bash
npm run test:db
```

Поднимает чистый `postgres:16` в Docker, накатывает три миграции в том же
порядке, что и Supabase, и проезжает по ним четыре сценария от имени двух
живых пользователей — с включённым RLS, то есть ровно с теми правами, что
у приложения по anon-ключу.

Прогонять **до** пуша: деплой применяет миграции к настоящей базе, и
отменить это одним нажатием нельзя.

| Сценарий | Что проверяет |
|---|---|
| `20_happy_path` | петля «выложил → забронировали → вернули → оценили», все суммы |
| `30_guards` | верификация, подделка личности, двойное бронирование, чужие данные |
| `40_overdue` | напоминания, автоспор о невозврате, закрытие по таймеру |
| `50_disputes` | порча, порог 15 000 ₸, авторешение, модерация, компенсации |

`db-tests/00_platform_shim.sql` подделывает то, что на реальном проекте даёт
платформа: схему `auth` с `auth.uid()`, схему `storage` и роли
`anon`/`authenticated` с дефолтными грантами. Бизнес-логика при этом
настоящая — тестируются ваши триггеры, политики и RPC.

Стенд лежит в `db-tests/`, а не в `supabase/tests/`, намеренно: последнюю
папку Supabase CLI резервирует под pgTAP-тесты и умеет выполнять командой
`supabase test db`. Наши сценарии не pgTAP — они заводят пользователей и
сделки, и запуск их против рабочей базы был бы неприятным сюрпризом.
В `supabase/` лежит только то, чем распоряжается сама платформа.

Чего стенд принципиально не покажет, и что придётся увидеть только на живом
проекте: право `postgres` вешать триггер на `auth.users` (там владелец —
`supabase_auth_admin`) и создавать политики на `storage.objects`, работу
PostgREST и SMS-провайдера. Для этого есть `db-tests/90_smoke_live.sql` —
запрос только читает системные каталоги, вставляется в SQL Editor и
показывает 14 проверок построчно.

Оставить базу для ручных запросов:

```bash
node db-tests/run.mjs --keep
```

## Дизайн

Правила, по которым сделаны экраны, собраны в [DESIGN.md](DESIGN.md): откуда
взят бренд, что значит каждый цвет, почему загрузка, пустота и сбой обязаны
выглядеть по-разному, и чек-лист для нового экрана.

Читать перед тем, как добавлять экран: правила там выведены из конкретных
ошибок, а не из вкуса, и половина из них про то, как не соврать человеку о
состоянии системы.

## Trust Score — где что лежит

Все правила реализованы в `supabase/migrations/20260816120100_trust_score.sql` как
функции и триггеры Postgres, а не в React-коде. Причина простая: к этой базе
позже подключится Telegram-бот, и правило, написанное в компоненте, он обойдёт.

| Правило | Реализация |
|---|---|
| 1. Без верификации нельзя сдавать и арендовать | `assert_verified()` + триггеры на `items` и `bookings` |
| 2. Рейтинг после `completed`, обе стороны | триггеры `reviews_validate`, `reviews_update_rating` |
| 3. Депозит `held` при бронировании | `bookings_before_insert()` |
| 4. Возврат вовремя → `released` | `booking_mark_returned()` → `booking_complete()` |
| 5. Просрочка → grace period → автоспор | `process_overdue_bookings()` |
| 6. Порча: фото «после» против фото «до» | `open_damage_dispute()` |
| 7. Порог 15 000 ₸: авторешение или модерация | `open_damage_dispute()` + `decide_dispute_payout()` |

### Закрытие сделки — один шлюз

Закрыть сделку хотят четверо: владелец кнопкой, авторешение спора, модератор
и планировщик по таймеру. Логика закрытия живёт в одном месте —
`settle_booking()`, — а четверо решают только **момент** вызова:

| Кто зовёт | Когда |
|---|---|
| `open_damage_dispute()` | сразу после авторешения: спор закрыт, ждать нечего |
| `resolve_dispute_manually()` | после решения модератора; `p_finalize => false` даёт паузу |
| `booking_complete()` | владелец нажал «всё в порядке» |
| `process_overdue_bookings()` | подметает всё созревшее одним проходом |

Шлюз сам проверяет, не держит ли сделку что-то ещё (`has_open_disputes()`),
начисляет компенсацию отдельной строкой и отпускает выплаты. Он идемпотентен:
повторный вызов на закрытой сделке ничего не делает.

Открытым считается только спор со статусом `manual_review`. `auto_resolved` и
`resolved` — уже закрытые: путать их с открытыми означало, что сделка с любой,
даже копеечной, претензией не закрывалась бы никогда.

### Каталог без входа — привилегии на колонки

Витрина открыта роли `anon`: человек должен увидеть, что перфораторы вообще
есть, до того как введёт номер и будет ждать SMS. Вход просят в последний
момент — на кнопке «Забронировать».

Тонкость, ради которой миграция написана именно так: **RLS фильтрует строки,
а не колонки**. Политика «читать всем» на `users` открыла бы строку целиком,
вместе с телефоном. Поэтому работают два разных механизма:

| Механизм | Что решает |
|---|---|
| Политика `users_read_anon` | какие *строки* видны — все |
| `grant select (id, full_name, rating, ...)` | какие *поля* доступны — без телефона |

Порядок обязателен: сначала `revoke select on users from anon`, потом грант
поимённо. Без revoke более широкое право, выданное дефолтными привилегиями
проекта, перекроет колоночное.

### Занятость объявления — исключение из RLS

Политика `bookings_read_participants` показывает бронь только её сторонам, и
это правильно: суммы и личности чужим знать незачем. Но у неё было тяжёлое
следствие — потенциальный арендатор видел **пустой** календарь занятости,
потому что для него запрос к `bookings` возвращал ноль строк. Он выбирал
занятые даты вслепую и упирался в `bookings_no_overlap` уже после нажатия
«Забронировать».

Ослаблять политику для этого нельзя. Вместо этого есть `item_busy_dates()` —
функция, отдающая ровно две колонки, начало и конец занятого интервала.
`security definer` здесь не дыра, а сужение: вернуть больше, чем описано
в `returns table`, она физически не может. Стенд проверяет и доступ
постороннего, и саму сигнатуру через `pg_get_function_result`.

Список живых статусов в ней обязан совпадать со списком в ограничении
`bookings_no_overlap`. Если они разъедутся, календарь начнёт врать
относительно того, что реально запретит база.

Пороги и проценты не зашиты в код — они в таблице `app_settings`, менять их
можно без деплоя приложения:

```sql
update app_settings set value = 6 where key = 'grace_period_hours';
```

### Регулярная задача

`process_overdue_bookings()` двигает сделки, у которых истекли сроки: шлёт
напоминания в день возврата, открывает автоспоры о невозврате, закрывает сделки,
по которым окно претензии прошло без спора. Запускать раз в час.

В Supabase — через **Database → Extensions → pg_cron**:

```sql
select cron.schedule('renthub-overdue', '0 * * * *', $$select process_overdue_bookings()$$);
```

## Пассивный режим владельца

Большинство владельцев ведут себя как «помесячные» арендодатели: хотят сдать
вещь и забыть, а не управлять каждой сделкой. Поэтому «Мои вещи» построен как
готовый итог — «вот что произошло, пока вас не было», — а не как дашборд с
контролем. Владельца дёргают только там, где без него сделку не сдвинуть:
подтвердить бронь и принять вернувшуюся вещь. Календарь занятости существует и
показывает реальные данные, но это опциональная деталь, а не то, что владелец
обязан открывать.

Таблица `notifications` — общая точка для приложения и будущего бота: бот
забирает записи с пустым `sent_at` и рассылает их в Telegram.

## Бизнес-модель (расчёты, без реальных транзакций)

- Комиссия платформы: **20%** от `daily_price × дни`
- Страховой сбор: **+150 ₸** фиксированно, если арендатор выбрал защиту
- Владельцу: сумма аренды минус комиссия
- Компенсация ущерба: **отдельной строкой** в `payouts` (`kind =
  'damage_compensation'`), комиссия с неё не берётся

Две строки вместо одной — чтобы владелец в «Моих вещах» видел, из чего
сложилась сумма, и не открывал спор ради этого. Экран показывает
«из них компенсации ущерба» отдельно.

Расчёт продублирован в `src/lib/pricing.ts` — чтобы показать сумму до создания
брони. Авторитет остаётся за базой: клиент не отправляет суммы, их проставляет
триггер из цены объявления.

- Реальные платежи и эскроу

- Доставка и логистика силами платформы
- ID-верификация (только телефон)
- Чат между владельцем и арендатором

  `schedule_payouts()`

## Открытые вопросы

- ~~**Город пилота**~~ — решён: **Кокшетау**. Значение живёт в двух местах,
  и они обязаны совпадать: `EXPO_PUBLIC_PILOT_CITY` в `.env` и дефолт колонки
  `items.city` в базе. Разойдутся — объявления будут создаваться в одном
  городе, а искаться в другом, и витрина окажется пустой при полной базе.
- **Сумма авторешения спора** — платформа удерживает меньшее из заявленного
  ущерба и депозита. Альтернативы описаны в комментарии к
  `decide_dispute_payout()`.
- **Сколько фото требовать** при публикации — сейчас минимум одно; компромисс
  описан над `validateNewItem()` в `app/item/new.tsx`.
- **Часовой пояс дедлайнов.** `grace_period_ends_at` считается как
  `(end_date + 1)::timestamptz`, то есть от полуночи по часовому поясу
  сервера. На Supabase это UTC, и при `grace_period_hours = 12` дедлайн
  приходится на **17:00 по Алматы**, а не на 12:00, как читается из настройки.
  Пять лишних часов в пользу арендатора. Если нужна привязка к местным суткам:
  `(end_date + 1)::timestamp at time zone 'Asia/Almaty'`. Решать после того,
  как назван город пилота.
- **Отмена заявки меняет не только статус.** Политика `bookings_cancel_pending`
  проверяет в `with check` только `renter_id` и `status`, поэтому арендатор
  может тем же UPDATE переписать суммы своей неподтверждённой брони
  (проверено: `renter_total` меняется на любое значение). Сейчас безвредно —
  деньги не двигаются, а отменённая бронь ни на что не влияет. Станет важным
  на этапе реальных платежей, когда суммы отменённых броней начнут читаться
  при возвратах.
