# RentHUB

P2P-аренда вещей, Казахстан. Пилот — узкая ниша: строительная техника и инструмент,
один город.

**Этап: MVP без реальных платежей.** Бронирования, депозиты и выплаты полностью
живут в базе как статусы, но деньги не двигаются. Смысл этапа — проверить, что
работает петля «выложил → нашли → забронировали → вернули», а не гладкость
платежей. Kaspi Pay / CloudPayments подключаются отдельным этапом, когда петля
подтверждена живыми людьми.

Продолжаете работу в новой сессии? — [HANDOFF.md](HANDOFF.md): состояние
проекта, команды, ограничения и готовый промпт.

## Стек

| Слой | Технология |
|---|---|
| Клиент | Expo (React Native + TypeScript) — один код на iOS, Android и веб |
| Навигация | expo-router (файловая маршрутизация) |
| Бэкенд | Supabase: Postgres + Auth (код в Telegram) + Storage для фото |
| Уведомления и вход | Telegram-бот на aiogram — та же база, см. bot/ |

Бэкенд один. Приложение и будущий бот — два разных «окна» в него, а не два
отдельных проекта.

## Запуск

```bash
npm install
```

1. Создайте проект на [supabase.com](https://supabase.com). При создании
   **оставьте включённой** галочку «Automatically expose new tables»: в
   миграциях нет ни одного `grant`, доступ разграничен политиками RLS. Без
   неё приложение получит `permission denied for table items` при верных
   политиках.
2. Схема приезжает пушем — см. «Миграции и деплой» ниже.
3. Включите вход по телефону: **Authentication → Providers → Phone**. SMS-провайдер
   не нужен — коды доставляет бот в Telegram через Send SMS Hook, см. раздел
   «Вход по коду через Telegram».
4. Скопируйте `.env.example` в `.env` и подставьте URL и anon-ключ из
   **Project Settings → API**. Переменные `EXPO_PUBLIC_` вшиваются в бандл при
   сборке, поэтому после правки `.env` сервер надо перезапустить — на живом
   он подхватит только старые значения.

```bash
npm run web      # веб-версия в браузере
npm start        # QR-код для Expo Go на телефоне
```

## Миграции и деплой

Схема живёт в `supabase/migrations/` и приезжает на проект **пушем в `main`**:
подключена GitHub-интеграция Supabase, она сверяет папку с таблицей
`supabase_migrations.schema_migrations` и выполняет только новое.

Отсюда одно правило, нарушать которое дорого:

> **Не менять схему через SQL Editor.** Правки мимо миграций не попадают в
> учёт, и следующий деплой падает с ошибкой синхронизации. Любое изменение —
> новый файл в `supabase/migrations/`, проверенный локально и отправленный
> пушем.

Имена файлов — временные метки (`20260816120000_schema.sql`), этого требует
Supabase CLI: по ним определяется порядок и ведётся история.

## Проверка миграций

```bash
npm run test:db
```

Поднимает чистый `postgres:16` в Docker, накатывает три миграции в том же
порядке, что и Supabase, и проезжает по ним четыре сценария от имени двух
живых пользователей — с включённым RLS, то есть ровно с теми правами, что
у приложения по anon-ключу.

Прогонять **до** пуша: деплой применяет миграции к настоящей базе, и
отменить это одним нажатием нельзя.

| Сценарий | Что проверяет |
|---|---|
| `20_happy_path` | петля «выложил → забронировали → вернули → оценили», все суммы |
| `30_guards` | верификация, подделка личности, двойное бронирование, чужие данные |
| `40_overdue` | напоминания, автоспор о невозврате, закрытие по таймеру |
| `50_disputes` | порча, порог 15 000 ₸, авторешение, модерация, компенсации |

`db-tests/00_platform_shim.sql` подделывает то, что на реальном проекте даёт
платформа: схему `auth` с `auth.uid()`, схему `storage` и роли
`anon`/`authenticated` с дефолтными грантами. Бизнес-логика при этом
настоящая — тестируются ваши триггеры, политики и RPC.

Стенд лежит в `db-tests/`, а не в `supabase/tests/`, намеренно: последнюю
папку Supabase CLI резервирует под pgTAP-тесты и умеет выполнять командой
`supabase test db`. Наши сценарии не pgTAP — они заводят пользователей и
сделки, и запуск их против рабочей базы был бы неприятным сюрпризом.
В `supabase/` лежит только то, чем распоряжается сама платформа.

Чего стенд принципиально не покажет, и что придётся увидеть только на живом
проекте: право `postgres` вешать триггер на `auth.users` (там владелец —
`supabase_auth_admin`) и создавать политики на `storage.objects`, работу
PostgREST и SMS-провайдера. Для этого есть `db-tests/90_smoke_live.sql` —
запрос только читает системные каталоги, вставляется в SQL Editor и
показывает 14 проверок построчно.

Оставить базу для ручных запросов:

```bash
node db-tests/run.mjs --keep
```

## Что уже работает

Экраны в порядке из ТЗ:

1. **Вход по телефону** — `app/sign-in.tsx`. Код из SMS. Подтверждение номера и
   есть верификация на MVP.
2. **Каталог** — `app/(tabs)/index.tsx`. Поиск + фильтр по категориям. Поиск
   идёт по названию, описанию и ориентиру: «Васильковский» — это запрос не
   про инструмент, а про то, куда за ним ехать.
3. **Карточка объявления** — `app/item/[id].tsx`. Фото, цена, рейтинг владельца,
   календарь занятости, расчёт стоимости и бронирование. Внизу — другие вещи
   той же категории: без них карточка была тупиком «бронировать или назад».
4. **Создание объявления** — `app/item/new.tsx`. Фото «до», цена, депозит,
   ориентир «где забирать».
5. **Мои аренды** / **Мои вещи** — `app/(tabs)/bookings.tsx`,
   `app/(tabs)/my-items.tsx`.
6. **Профиль** — `app/(tabs)/profile.tsx`. Рейтинг, история, пассивный режим.

Плюс экран сделки `app/booking/[id].tsx`, где живут все переходы статусов,
претензия по порче и отзывы.

### Две вещи, без которых сделка не доходит до конца

**Где забирать** — `items.pickup_area`, свободный текст вроде «мкр.
Васильковский» или «возле вокзала». Лендинг обещает «инструмент рядом», а
до этого поля в каталоге не было ничего о том, насколько рядом: вещь надо
забрать и вернуть, и «через дорогу» против «через весь город» меняет
решение сильнее, чем двести тенге в цене. Справочника районов у пилота
нет — выдуманный заставил бы владельца выбирать между пунктами, которые
не описывают его двор.

**Контакт второй стороны** — `booking_contact()`. Телефон закрыт грантом
на колонки не только анониму, но и любому вошедшему, и это правильно:
витрина не место для чужих номеров. Но вещь передают из рук в руки, и у
сторон состоявшейся сделки задача другая. Функция отдаёт контакт ровно
того, с кем у вызывающего общая бронь, и только после подтверждения: до
него владелец ещё ничего не обещал, а заявка не должна работать способом
собирать телефоны.

## APK для Android

Веб-версия открывается по ссылке, но первым владельцам в Кокшетау часто
привычнее получить файл в мессенджере. Сборка идёт в облаке Expo:

```bash
npm install -g eas-cli
eas login                                  # нужен бесплатный аккаунт expo.dev
eas env:push preview --path .env --force   # адрес и anon-ключ Supabase — в облако
npm run apk                                # eas build -p android --profile preview
```

Через 10–20 минут придёт ссылка на готовый APK — её можно переслать кому
угодно, установка без Google Play.

Профиль `preview` собирает именно APK, а не AAB: пакет для Play Store
устанавливается только через магазин, а нам нужен файл, который человек
откроет из чата.

Собирать в облаке, а не локально, потому что локальная сборка требует
Android SDK и Java — около 10 ГБ инструментов ради файла, который нужен
раз в неделю.

Профиль `production` собирает AAB для публикации в Play Store — понадобится,
когда пилот подтвердится и вы решите выходить в магазин.

### Переменные окружения сборки

`.env` лежит в `.gitignore`, а EAS забирает проект по git — игнорируемые файлы
на сервер сборки не уезжают. `src/lib/supabase.ts` при пустом адресе бросает
исключение на первом же импорте, и пропажа выглядит хуже обычной ошибки: сборка
проходит успешно, ссылка приходит, а APK падает при запуске. Узнаёте вы об этом
через двадцать минут после старта.

Поэтому значения живут в окружениях EAS, а профиль в `eas.json` ссылается на своё
окружение полем `environment`. Выложить их туда — один раз:

```bash
eas env:push preview --path .env --force   # прочитает .env и зальёт в окружение
eas env:list preview                       # проверить, что все четыре на месте
```

Профиль `production` читает окружение `production`: перед первой сборкой для Play
Store туда нужно выложить то же самое, иначе AAB выйдет с теми же последствиями.

Смысл здесь не в секретности — anon-ключ публичный по замыслу и всё равно вшит
и в APK, и в веб-сборку в `docs/`. Смысл в одном месте хранения: правка `.env`
доезжает до сборки одной командой, а не правкой ещё и `eas.json`.

### Обновления без переустановки

```bash
npm run update      # eas update --channel preview
```

Правки в коде уезжают в уже установленные приложения — человек получает их
при следующем запуске, пересобирать и рассылать APK заново не нужно. Это
важнее, чем кажется: без обновлений каждая опечатка означала бы новую
рассылку файла и просьбу переустановить.

Поддержку обновлений нельзя добавить в уже собранный APK — она вшивается
в сборку. Поэтому `expo-updates` подключён **до** первой сборки.

По воздуху уезжает только JavaScript. Если менялась нативная часть — новые
пакеты, права, плагины — нужна новая сборка. Связь описывает
`runtimeVersion: appVersion` в `app.json`: старые сборки не увидят
несовместимое обновление вместо того, чтобы упасть на нём.

Адрес сервера обновлений и идентификатор проекта записаны в `app.json` —
`updates.url` и `extra.eas.projectId`. Второе добавляет `eas init --id`, первое —
только `eas update:configure`. Забыть первое дорого: сборка пройдёт, APK уедет
людям, а `npm run update` будет публиковать обновления, за которыми никто не
приходит.

## Приглашения, модераторы, демо

Пилот идёт по закрытым приглашениям: SMS-провайдер для Казахстана стоит
$250 в месяц только за регистрацию имени отправителя, и до первых живых
сделок это бессмысленно.

```bash
npm run invite -- +77011234567 "Имя Фамилия"   # завести участника, выдать пароль
npm run invite -- +77011234567 "Имя" a@mail.com  # то же плюс вход по почте
npm run moderator -- +77011234567              # право разбирать споры
npm run demo:fill                              # витрина для показа продукта
npm run demo:clear                             # убрать её
npm run icons                                  # пересобрать иконки и og:image
npm run demo:photos                            # нарисовать заглушки для витрины
npm run queue                                  # кто оставил заявку и ждёт приглашения
npm run check:bot                              # два имени в боте и списки статусов против базы
npm run check:pitch                            # сходятся ли числа деки между собой и с кодом
npm run health                                 # живо ли то, что обещано словами
npm run auth                                   # адрес возврата и срок жизни кода входа
npm run nudge                                  # кому написать про Telegram и каким текстом
```

Все шесть требуют секретного ключа: он обходит RLS, и в `.env` ему нельзя —
этот файл вшивается в бандл и уезжает в браузер. Ключ лежит в `.env.secret`,
который читают только скрипты из `scripts/`:

```
SUPABASE_SECRET_KEY=sb_secret_...
```

Файл в `.gitignore`. Разово его перебивает переменная окружения — например,
когда команда идёт против другой базы:

```bash
$env:SUPABASE_SECRET_KEY="sb_secret_..."; npm run invite -- +7701... "Имя"
```

Обратная сторона решения: ключ в файле доступен любому процессу, запущенному
в этой папке, — в том числе агенту, если попросить его выполнить команду.
Раньше ключ жил только внутри одной сессии PowerShell. Для машины, за которой
вы сидите один, это разумный размен: набранный вручную ключ всё равно оседал
в истории команд, за которой никто не следит.

Демо-объявления берут фото из `demo-photos/` — свои, а не стоковые, и
создаются под отдельным владельцем, поэтому удаляются одной командой и
не задевают настоящие.

## Бот в Telegram

Второе окно в ту же базу. Живёт в [bot/](bot/README.md), запускается отдельно:

```bash
python -m pip install -r bot/requirements.txt
python bot/bot.py
```

Работает и проверено на живом проекте: человек открывает бота, нажимает
«Поделиться номером» — Telegram отдаёт номер, подтверждённый им самим, — и
бот записывает `telegram_id` в профиль. После этого уведомления о сделках
приходят в Telegram: бот забирает из `notifications` записи с пустым
`sent_at` и ставит отметку о доставке.

Это закрывает главную статью расходов пилота. SMS-провайдер для Казахстана
стоит $250 в месяц только за регистрацию имени отправителя, а Telegram даёт
более сильное подтверждение бесплатно: код из SMS доказывает владение симкой
в момент ввода, а Telegram проверил номер при регистрации и хранит эту связь.

Ограничение, которое не обойти: **бот не может написать первым**. Telegram
запрещает боту слать сообщение тому, кто сам не начинал диалог. Поэтому
любой сценарий начинается с того, что человек открывает бота, и ссылку на
него стоит держать на видном месте в приложении и на лендинге.

Проверить всю цепочку «база → бот → Telegram» без создания сделки:

```bash
npm run notify:test -- +77011234567     # положить проверочное уведомление
npm run notify:clear                    # убрать все проверочные
```

### Вход по коду через Telegram

`supabase/functions/telegram-otp/` — Send SMS Hook: Supabase генерирует код,
проверяет его и считает попытки сам, а функция только доставляет его в Telegram
вместо SMS. Приложение при этом не меняется: на экране входа остаётся тот же
`signInWithOtp({ phone })`, вкладка «По SMS» включается сменой
`EXPO_PUBLIC_AUTH_MODE=sms`.

Пилот при этом остаётся закрытым сам собой: код уходит только тому, у кого в
профиле есть `telegram_id`, а он появляется лишь после «Поделиться номером» у
заведённого участника. Посторонний получит понятный отказ, а не молчание.

**Функцию не разворачивает GitHub-интеграция** — она применяет только
миграции. Порядок ручной, шесть шагов:

```bash
npx supabase login
npx supabase link --project-ref owfsfwqwulpossjbnprp
npx supabase functions deploy telegram-otp --no-verify-jwt
```

Флаг `--no-verify-jwt` обязателен: хук вызывает функцию от имени платформы, а
не пользователя, и проверка пользовательского токена отклонила бы каждый
вызов.

Дальше в панели Supabase:

1. **Authentication → Providers → Phone** — включить (провайдер SMS при этом
   не настраивается, его заменяет хук).
2. **Authentication → Hooks → Send SMS** — тип **HTTPS**, адрес
   `https://owfsfwqwulpossjbnprp.supabase.co/functions/v1/telegram-otp`.
   Панель покажет секрет вида `v1,whsec_…` — скопировать.
3. Отдать функции секрет и токен бота:

```bash
npx supabase secrets set SEND_SMS_HOOK_SECRET=v1,whsec_... TELEGRAM_BOT_TOKEN=...
```

4. Переключить приложение: `EXPO_PUBLIC_AUTH_MODE=sms` в `.env`, затем
   `eas env:push preview --path .env --force` и `npm run update`.

Развёрнуто и проверено 21.08.2026: запрос кода на номер участника с
привязанным Telegram доходит до бота за секунды. Функция при этом не хранит
ничего — ни кодов, ни попыток: этим занимается сам Supabase.

Проверка: на экране входа вкладка «По SMS», номер участника с привязанным
Telegram → код приходит в бота.

Бот двигает и статусы сделок — с 28.08.2026. Переходы по-прежнему живут в
RPC и опираются на `auth.uid()`, которого у сервисного ключа нет; обёртки
`bot_*` выставляют `request.jwt.claims` (его и читает `auth.uid()`) и зовут
**ту же** функцию, что зовёт приложение. Правило остаётся одно на два входа:
«подтверждать бронь может только владелец» — это ответ `booking_confirm()`,
а не проверка в Python.

Прав это боту не добавляет: сервисный ключ и так обходит RLS целиком, прямой
`update bookings` был доступен и раньше — мимо всех проверок. Обёртка не
расширяет доступ, а сужает. Право вызвать любую `bot_*` равно праву
действовать от чужого имени, поэтому у них явный `revoke` для `anon` и
`authenticated`, и стенд это проверяет.

Побочный эффект, который стоило бы сделать и без бота: отмена брони, отзыв и
публикация объявления переехали из прямых запросов в RPC — под сервисным
ключом RLS не применяется, а роль внутри `security definer` не переключить.
Заодно из аргументов ушли владелец (берётся из `auth.uid()`) и город
(ставит база), а `booking_cancel()` больше не позволяет переписать суммы
отменяемой брони — см. «Открытые вопросы» ниже.

## Вход по почте

Третий способ войти, рядом с приглашением и Telegram. Нужен ровно для
одного случая: у человека нет Telegram или он до него не дошёл.

**Работает только для привязанного адреса.** Ключ к этому — один параметр:

```ts
supabase.auth.signInWithOtp({ email, options: { shouldCreateUser: false } })
```

Без него Supabase заводит нового пользователя под незнакомый адрес, и
человек, набравший почту, которую к аккаунту не привязывал, молча получил бы
**второй** аккаунт: свой `id`, пустой профиль, ни сделок, ни рейтинга. Он бы
решил, что приложение потеряло его данные, и был бы почти прав.

Причина, по которой это не абстрактный риск: поле `email` в `auth.users`
здесь уже занято служебным адресом вида `77010000001@renthub.test` — его
собирает `inviteEmail()` из номера, и он же служит логином для входа по
приглашению. Настоящая почта попадает в то же поле, второго под неё нет.

Отсюда два следствия, каждое видно на экране:

- **Почту привязывает сам человек** — в профиле, карточка «Почта для входа».
  Supabase шлёт письмо подтверждения, адрес меняется только после перехода
  по ссылке. Админ-скриптом за человека это делать странно: почта — личные
  данные, и он должен её знать, чтобы ею войти.
- **После привязки пароль из приглашения работает с новой почтой**, а не с
  номером телефона: адрес учётной записи и есть логин. Экран профиля
  предупреждает об этом рядом с кнопкой, а не в общей справке.

Новых участников можно заводить сразу с настоящим адресом:

```bash
npm run invite -- +77011234567 "Ержан Ахметов" erzhan@gmail.com
```

Почта распознаётся по «@», а не по позиции аргумента.

### Что настроить в панели Supabase

Настройки, которые продукт обещает словами, а держит снаружи кода,
проверяет и правит одна команда:

```bash
npm run auth
```

Проверяет она две вещи: куда на самом деле ведёт ссылка из письма и
сколько живёт код входа — сверяя это с тем, что обещают приложение и текст
функции `telegram-otp`. С токеном аккаунта в `.env.secret` та же команда с
`-- --apply` **правит сама**: меняет три поля и **дополняет** список
редиректов, а не заменяет его.

Состояние хука Send SMS снимается до правки и сверяется после — расхождение
останавливает работу. Через этот хук приходят коды входа в Telegram, и
сломать его молча означало бы сломать вход.

Устроено так намеренно. Настройку должны уметь оба: человек у панели и
агент в терминале. Проверка при этом одна и та же, поэтому «сделано» не
зависит от того, кто нажимал — и не требует верить на слово. Про второй
секрет и почему он необязателен — `.env.secret.example`.

Дальше — что именно там стоит, если делать руками. Отправка писем работает
**без своего SMTP** — встроенным сервисом, ничего подключать не нужно.
Настроек три, все в **Authentication**:

1. **URL Configuration → Site URL** — адрес, куда возвращает ссылка из
   письма: `https://mandaloriancs.github.io/renthub/app/` для публикации,
   `http://localhost:8081` для локальной разработки.
2. **URL Configuration → Redirect URLs** — каждый адрес в своём поле:
   `http://localhost:8081`, `http://localhost:8081/**`,
   `https://mandaloriancs.github.io/renthub/app/**`.
3. **Sign In / Providers → Email** — провайдер включён по умолчанию;
   проверьте, что он не выключен.

Три вещи, на которых спотыкаются:

- **Переключатель не сохраняется сам.** Флажок выглядит включённым, пока не
  нажата зелёная «Save changes» внизу страницы. У Site URL при этом своя
  кнопка сохранения, независимая от списка Redirect URLs.
- **В письме приходит ссылка, а не код.** На встроенной отправке шаблоны
  править нельзя — панель прямо пишет `Set up custom SMTP to edit templates`,
  а стандартный шаблон содержит `{{ .ConfirmationURL }}`. Переделывать ничего
  не надо: экран входа принимает оба исхода и говорит об этом честно.
  Переход по ссылке и ввод кода дают одну и ту же сессию.
- **Лимит — несколько писем в час.** Встроенная отправка заявлена как «только
  для разработки». Проверить вход хватит; на демо, где к продукту подойдут
  пять человек подряд, — нет. Обнаруживается это в худший момент: письма
  просто перестают приходить, без ошибки в приложении.

### Почему письма не приходят — и что это чинит

**Измерено 04.09.2026 на живом проекте.** Диагноз важен, потому что «письма
нет» бывает по четырём разным причинам, и три из них не про почту:

| Что вернул Supabase | Что это значит |
|---|---|
| `422 otp_disabled` | адрес не привязан к аккаунту — так и задумано, см. выше |
| `429 over_email_send_rate_limit` | минута защиты от перебора на один адрес |
| `429 email rate limit exceeded` | исчерпана часовая квота встроенной отправки |
| **`200` и пустой ответ** | **заявка принята, дальше дело за доставкой** |

Живой проект отвечает `200` за ~1 секунду, а `429` приходит только со
второго запроса в минуту. То есть **приложение и Supabase ни при чём**.

**И письмо доходит.** Это проверено на живой почте 04.09.2026: письмо от
`noreply@mail.app.supabase.io` с заголовком «Your sign-in link» приходит за
секунды. Первый диагноз («не доставляет встроенный сервис») оказался
неверным, и хорошо, что нашлось письмо, а не рассуждение.

**Ломается следующий шаг: ссылка ведёт на `http://localhost:3000`.**
Человек нажимает «Sign in» и попадает на несуществующий адрес, а при
повторном нажатии — ещё и на `otp_expired`, потому что токен одноразовый и
сгорел на первом переходе.

Измерено `admin.generateLink` — он возвращает ту самую ссылку, не отправляя
письма:

```
без redirectTo                    → redirect_to = http://localhost:3000
с redirectTo на адрес приложения  → redirect_to = http://localhost:3000
```

Первая строка — Site URL проекта, оставшийся по умолчанию. Вторая говорит
больше: **запрошенный адрес подменён**, потому что его нет в списке Redirect
URLs. GoTrue не отказывает — он молча берёт Site URL.

**Чинится одной настройкой**, и без неё не помогает никакой код. Двумя
путями на выбор:

```bash
npm run auth             # покажет, что нажать в панели
npm run auth -- --apply  # сделает сам, если есть токен аккаунта
```

Руками это **Authentication → URL Configuration**: `Site URL` =
`https://mandaloriancs.github.io/renthub/app/`, а в `Redirect URLs` — тот же
адрес плюс `.../app/**` и `http://localhost:8081` с `**` для локальной
разработки. Команда печатает этот список сама, чтобы не сверять его глазами.

Проверить, что подействовало: та же команда без `--apply`, либо
`npm run health` — строка «ссылка из письма» показывает, куда она ведёт на
самом деле, и зеленеет, когда возвращает в приложение. Важно, что проверка
не зависит от способа: она спрашивает Supabase, а не верит тому, кто нажимал.

**Сделано 05.09.2026.** До правки список Redirect URLs был **пуст** — это и
есть причина, по которой явно запрошенный адрес подменялся.

### Сколько живёт код входа

Функция `telegram-otp` называет срок словами прямо в сообщении, и 05.09.2026
эти слова врали: текст обещал «Действует час», а `sms_otp_exp` в проекте
стоял **60 секунд**. Обе стороны по отдельности безупречны — текст вежлив,
настройка допустима. Врёт их сочетание, и узнаёт об этом человек,
вернувшийся к коду через пять минут.

Теперь срок — 600 секунд, и правда о нём лежит в `shared/auth.json`:
число для настройки и те же слова для текста. `npm run auth` сверяет обе
стороны, `-- --apply` чинит настройку; текст функции доезжает отдельно —
`npx supabase functions deploy telegram-otp`.

Десять минут, а не час: код приходит в Telegram, а вводится в приложении,
и человеку нужно переключиться между приложениями и набрать шесть цифр.
Минуты на это мало, часа не нужно.

Со стороны кода сделано всё, что можно: приложение просит правильный адрес
возврата (`EMAIL_RETURN_URL`), а если ссылка всё же вернулась с отказом —
экран входа читает его из хвоста адреса и объясняет по-русски, вместо того
чтобы молча показать витрину невошедшему.

**Свой SMTP при этом всё равно нужен** — но не для того, чтобы письма
доходили, а чтобы снять лимит встроенной отправки и заменить ссылку кодом.

### Свой SMTP

Это единственное, что чинит почту. Даёт три вещи разом: снимает лимит,
разблокирует шаблоны (то есть код вместо ссылки) и позволяет писать с
собственного адреса.

**Быстрый путь, без домена и без DNS — минут пять.** Годится для пилота и
для демо; собственный домен нужен позже, когда писем станет много.

Подойдёт обычный ящик Gmail с паролем приложения:

1. В аккаунте Google включить двухэтапную проверку, затем создать **пароль
   приложения** (Google Account → Security → App passwords). Обычный пароль
   от почты SMTP не примет.
2. **Project Settings → Authentication → SMTP Settings** в панели Supabase:

   | Поле | Значение |
   |---|---|
   | Host | `smtp.gmail.com` |
   | Port | `587` |
   | Username | ваш адрес `@gmail.com` |
   | Password | пароль приложения из шага 1 |
   | Sender email | тот же адрес |
   | Sender name | `RentHUB` |

3. Сохранить и проверить: `npm run health` покажет строку «почта», а живая
   проверка — запросить код на свой адрес на вкладке «Почта».

Ограничение этого пути: Gmail отправляет около 500 писем в сутки и ставит
своим адресом отправителя. Для пилота в одном городе этого с запасом.

**Путь для роста — свой домен.** Resend даёт 3000 писем в месяц бесплатно,
но требует подтвердить домен записями DNS: это единственный по-настоящему
долгий шаг, DNS обновляется часами. Поля в панели те же.

**После подключения любого из них** станут доступны **Authentication →
Email Templates**. Вкладка **Magic Link** — та, которую использует
`signInWithOtp({ email })`. Заменить `{{ .ConfirmationURL }}` на
`{{ .Token }}`, и в письме будет код, а не ссылка.

Проверить, что запрос вообще принят, можно не дожидаясь письма:

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  -X POST "https://owfsfwqwulpossjbnprp.supabase.co/auth/v1/otp" \
  -H "apikey: <anon-ключ>" -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","create_user":false}'
```

`200` означает, что приложение и Supabase ни при чём и разбираться надо с
доставкой. Ошибка означает обратное.

## Поддержка: две двери, одно правило

Человеку есть кому написать из обеих точек входа — из чата и из приложения,
`app/support.tsx`. Ответ уходит обратно через `moderator_notify()`, то есть
в `notifications`: и в ленту приложения, и в Telegram, если он привязан.
Отдельного канала связи нет и не нужно.

| Дверь | Функция | Кто автор |
|---|---|---|
| Telegram | `submit_support_message(p_actor, p_text)` | приходит аргументом — только сервисный ключ |
| Приложение | `support_submit(p_text)` | `auth.uid()` — доступна вошедшему |

Правило приёма общее и живёт в `support_add()`: длина текста и предел в три
открытых обращения на человека. Предел не от недоверия — без него один
расстроенный участник за минуту превращает очередь модерации в свою
переписку. Записанный дважды, он однажды разошёлся бы, и очередь топили бы
из той двери, где его забыли поднять.

**Верификации и блокировки на этих дверях нет намеренно.** Человек,
застрявший на подтверждении номера, и человек, заблокированный по ошибке, —
ровно те, кому написать нужнее всего. Стенд это закрепляет: в коде «забыли
добавить `assert_verified`» и «намеренно не добавили» выглядят одинаково.

**Чего экран не делает:** не показывает ответ рядом с вопросом.
`moderator_notify()` не знает, на какое обращение отвечает — такого поля у
него нет, — и связать их можно было бы только по времени, то есть угадать.
Угаданная связь хуже честного «ответ придёт в уведомления».

## Снятие объявления модератором

Модератор снимает объявление функцией `moderator_hide_item()`, возвращает
право на публикацию — `moderator_restore_item()`.

**Почему это не просто `status = 'hidden'`.** До 01.09.2026 было именно так,
и в этом была дыра. У `item_status` два значения, и `hidden` означало сразу
две разные вещи: «владелец поставил на паузу» и «модератор снял с
публикации». Раз состояния неразличимы, неразличимы и права на выход из
них: политика `items_update_own` разрешает владельцу менять свою строку
целиком, и в «Моих вещах» это один значок глаза. Модератор снял — владелец
вернул, и по кругу. Модератор об этом даже не узнавал.

Теперь есть отдельная отметка `items.moderated_at`. Не новое значение
enum: миграции Supabase идут в транзакции, а значение, добавленное через
`alter type ... add value`, в этой же транзакции использовать нельзя.
Колонка обходит ловушку и вдобавок помнит, когда и почему.

Сторожит отметку триггер `items_verify_owner` — тот же, что уже стоит
перед каждой записью в `items` из приложения и из бота. Он запрещает две
вещи: ставить `status = 'active'`, пока отметка стоит, и менять саму
отметку. Второе не менее важно первого: политика разрешает менять строку
целиком, и без этого запрета обойти первый можно было бы, обнулив
`moderated_at` тем же `update`.

**Что владельцу можно.** Всё остальное: описание, цену, фото, ориентир.
Именно этим он и отвечает на замечание. Запрет на правку превратил бы
снятие с публикации в приговор без обжалования, а модерацию без пути
назад — в удаление.

**Что происходит после снятия ограничения.** Объявление остаётся скрытым.
«Теперь можно» и «публикую» — разные решения, и второе принимает владелец:
он мог за это время передумать сдавать вещь. Публикация чужой вещи от лица
модератора была бы действием за человека.

Список снятых объявлений — на экране модерации, над участниками. Без него
`moderator_restore_item()` была бы дверью без ручки: модератор снял
объявление и потерял его из виду навсегда.

## Блокировка участника

Модератор закрывает человеку сдачу и аренду функцией `set_user_blocked()`.
Три следствия, каждое выбрано осознанно:

**Активные объявления снимаются с публикации.** Иначе наказания нет: человек
не может выложить новое, а старые продолжают бронировать — на другом конце
сделки оказывается тот, кому платформа уже не доверяет.

**Разблокировка объявления не возвращает.** За время блокировки вещь могла
быть продана, сломана или сдана иначе. Молча вернуть её в витрину — значит
выставить на аренду то, чего, возможно, уже нет. Возврат делает владелец.

**Существующие брони не трогаются.** Заблокировать не значит отменить
обязательства: вещь на руках, депозит удержан, сделку надо довести до конца.
Иначе блокировка стала бы способом сорвать возврат — и ею бы для этого и
пользовались.

Запрет действует через `assert_verified()` — ту же точку, что проверяет
подтверждение номера. Это единственное место, которое нельзя обойти ни из
приложения, ни из бота, ни прямым запросом.

## Trust Score — где что лежит

Все правила реализованы в `supabase/migrations/20260816120100_trust_score.sql` как
функции и триггеры Postgres, а не в React-коде. Причина простая: к этой базе
позже подключится Telegram-бот, и правило, написанное в компоненте, он обойдёт.

| Правило | Реализация |
|---|---|
| 1. Без верификации нельзя сдавать и арендовать | `assert_verified()` + триггеры на `items` и `bookings` |
| 2. Рейтинг после `completed`, обе стороны | триггеры `reviews_validate`, `reviews_update_rating` |
| 3. Депозит `held` при бронировании | `bookings_before_insert()` |
| 4. Возврат вовремя → `released` | `booking_mark_returned()` → `booking_complete()` |
| 5. Просрочка → grace period → автоспор | `process_overdue_bookings()` |
| 6. Порча: фото «после» против фото «до» | `open_damage_dispute()` |
| 7. Порог 15 000 ₸: авторешение или модерация | `open_damage_dispute()` + `decide_dispute_payout()` |

### Закрытие сделки — один шлюз

Закрыть сделку хотят четверо: владелец кнопкой, авторешение спора, модератор
и планировщик по таймеру. Логика закрытия живёт в одном месте —
`settle_booking()`, — а четверо решают только **момент** вызова:

| Кто зовёт | Когда |
|---|---|
| `open_damage_dispute()` | сразу после авторешения: спор закрыт, ждать нечего |
| `resolve_dispute_manually()` | после решения модератора; `p_finalize => false` даёт паузу |
| `booking_complete()` | владелец нажал «всё в порядке» |
| `process_overdue_bookings()` | подметает всё созревшее одним проходом |

Шлюз сам проверяет, не держит ли сделку что-то ещё (`has_open_disputes()`),
начисляет компенсацию отдельной строкой и отпускает выплаты. Он идемпотентен:
повторный вызов на закрытой сделке ничего не делает.

Открытым считается только спор со статусом `manual_review`. `auto_resolved` и
`resolved` — уже закрытые: путать их с открытыми означало, что сделка с любой,
даже копеечной, претензией не закрывалась бы никогда.

### Каталог без входа — привилегии на колонки

Витрина открыта роли `anon`: человек должен увидеть, что перфораторы вообще
есть, до того как введёт номер и будет ждать SMS. Вход просят в последний
момент — на кнопке «Забронировать».

Тонкость, ради которой миграция написана именно так: **RLS фильтрует строки,
а не колонки**. Политика «читать всем» на `users` открыла бы строку целиком,
вместе с телефоном. Поэтому работают два разных механизма:

| Механизм | Что решает |
|---|---|
| Политика `users_read_anon` | какие *строки* видны — все |
| `grant select (id, full_name, rating, ...)` | какие *поля* доступны — без телефона |

Порядок обязателен: сначала `revoke select on users from anon`, потом грант
поимённо. Без revoke более широкое право, выданное дефолтными привилегиями
проекта, перекроет колоночное.

### Права на функции — по умолчанию открыто всё

Та же ловушка, но на функциях, и она дороже. **Новая функция в `public`
доступна анониму, пока её явно не закрыли.** Двумя разными путями сразу:

| Кто выдал | Чем отобрать |
|---|---|
| Postgres — `execute` роли `PUBLIC` на каждую новую функцию | `revoke all on function … from public` |
| Supabase — `alter default privileges … grant all on functions to anon, authenticated` | `revoke execute on function … from anon, authenticated` |

**Нужны обе строки.** Первая не отбирает именной грант `anon`, вторая не
отбирает грант `PUBLIC`. Написать одну и решить, что закрыл, — самая
дешёвая из возможных ошибок, и 03.09.2026 выяснилось, что её сделали семь
миграций подряд. Измерено ролью `anon`, то есть публикуемым ключом из
бандла: посторонний менял цену чужого объявления с 5000 на 1, снимал чужое
объявление с публикации, читал телефоны заявителей и писал участникам
уведомления от имени платформы.

**Внутренняя проверка спасает не всегда.** Функции с параметром `p_actor`
принимают того, за кого действуют, аргументом: `bot_actor_ok()` проверяет
*жертву*, а не вызывающего. Опознать вызывающего в них нечем, поэтому
право позвать такую функцию равно праву быть другим человеком, и
единственная защита — грант.

**И `auth.uid() is null` не означает «свой».** До 03.09.2026
`assert_moderator()` пропускала любой вызов с пустым `auth.uid()`, считая
такой вызов сервисным ключом или планировщиком. У `anon` он тоже пуст — и
на этом держались все функции модератора разом. Различать надо роль:

```sql
if coalesce(current_setting('role', true), '') in ('anon', 'authenticated') then
  raise exception 'RENTHUB_FORBIDDEN: …';
end if;
```

`current_setting('role')` переживает вход в `security definer`: `SECURITY
DEFINER` меняет `current_user`, но не GUC `role`, который выставляет
PostgREST. Замер изнутри функции: `anon` → `role=anon`, вошедший →
`role=authenticated`, сервисный ключ → `role=service_role`, планировщик →
`role=none`.

**И сравнение с `auth.uid()` тоже не защищает — по другой причине.**
04.09.2026 нашлось продолжение той же истории, дороже прежнего. Проверка
владельца во всех переходах сделки написана так:

```sql
if v_b.owner_id <> auth.uid() then
  raise exception 'RENTHUB_FORBIDDEN: ...';
end if;
```

У анонима `auth.uid()` пуст, а `uuid <> null` в SQL даёт **не «истина», а
NULL** — и `if` не срабатывает вовсе. Условие выглядит верным, читается
верным и пропускает постороннего. Чтением кода это не находится: искать
надо запуском.

Измерено ролью `anon`, каждая функция — из статуса, в котором она
разрешена (иначе меряется не защита, а совпадение: отказ «ожидался статус
confirmed» приходит от проверки шага):

| Из статуса | Функция | Что вышло |
|---|---|---|
| `pending` | `booking_cancel` | чужая бронь отменена |
| `confirmed` | `booking_mark_picked_up` | стала `active` |
| `active` | `booking_mark_returned` | стала `returned` |
| `returned` | `booking_complete` | закрыта: депозит и выплаты отпущены |
| `returned` | `open_damage_dispute` | претензия подана от имени владельца |

Две последние двигают деньги: закрытие отпускает депозит мимо осмотра
владельца, а претензия ниже порога решается автоматически.

Закрыто миграцией `20260904110000_anon_cannot_move_deals.sql`: одна
проверка `assert_signed_in()` первой строкой в каждой такой функции.
**Правило, которое из этого следует: сравнение с `auth.uid()` защищает
только после явной проверки, что `auth.uid()` вообще есть.**

Стенд сторожит это правилом, а не списком: он берёт всё, что доступно
`anon`, отбрасывает читающие функции (`stable`, `immutable`) и требует от
остального отказа со словами «нужно войти».

Стенд сторожит это правилом, а не списком: в `db-tests/30_guards.sql`
перечислено то, что анониму **можно**, и новая функция без отзыва прав
уронит стенд. Отдельно проверяется, что ни одна функция с `p_actor` не
доступна сессионной роли, — и что таких функций не ноль, иначе проверка
зеленела бы на сломанном соглашении об имени.

### Занятость объявления — исключение из RLS

Политика `bookings_read_participants` показывает бронь только её сторонам, и
это правильно: суммы и личности чужим знать незачем. Но у неё было тяжёлое
следствие — потенциальный арендатор видел **пустой** календарь занятости,
потому что для него запрос к `bookings` возвращал ноль строк. Он выбирал
занятые даты вслепую и упирался в `bookings_no_overlap` уже после нажатия
«Забронировать».

Ослаблять политику для этого нельзя. Вместо этого есть `item_busy_dates()` —
функция, отдающая ровно две колонки, начало и конец занятого интервала.
`security definer` здесь не дыра, а сужение: вернуть больше, чем описано
в `returns table`, она физически не может. Стенд проверяет и доступ
постороннего, и саму сигнатуру через `pg_get_function_result`.

Список живых статусов в ней обязан совпадать со списком в ограничении
`bookings_no_overlap`. Если они разъедутся, календарь начнёт врать
относительно того, что реально запретит база.

### Настройки: какие меняются без деплоя, а какие нет

Пороги и проценты живут в таблице `app_settings`, и **база всегда считает по
ней**. Но три из пяти продублированы в клиентах — иначе экран не смог бы
показать сумму до создания брони, а лендинг не назвал бы её вовсе. Дубль
честный (авторитет за Postgres, клиент только показывает), но он означает,
что смена значения в базе меняет не всё:

| Ключ | Смена в `app_settings` | Что ещё придётся править |
|---|---|---|
| `grace_period_hours` | достаточно | лендинг: «даётся 12 часов» (текст) |
| `damage_claim_window_hours` | достаточно | лендинг: «окно на претензию — 48 часов» (текст) |
| `dispute_auto_threshold` | достаточно | подписи «до 15 000 ₸» на экране сделки и в модерации |
| `commission_pct` | **недостаточно** | `COMMISSION_PCT` в `src/lib/pricing.ts`, `0.8` и «20%» в `bot/bot.py`, лендинг |
| `insurance_fee` | **недостаточно** | `INSURANCE_FEE` в `src/lib/pricing.ts`, лендинг |

Последние две — те, что участвуют в расчёте, а не только в тексте. Поменяв
комиссию только в базе, вы получите худший из исходов: владелец видит на
экране публикации «вы получите 4000, комиссия 20%», а начислено ему будет
другое. Спорить он придёт с тем числом, которое видел.

Первые три безопаснее: клиент их не считает, только называет словами. Экран
не соврёт о деньгах — но напишет неверный срок, а это тоже обещание.

```sql
update app_settings set value = 6 where key = 'grace_period_hours';
```

### Потолок цены — не настройка, а ловушка для опечатки

Рядом с числами выше стоит ещё одно, и в `app_settings` его нет намеренно:
**1 000 000 ₸ за сутки** — верхняя граница цены объявления. Это не параметр
бизнес-модели, который кто-то станет крутить, а защита от лишнего нуля: цена
с ним не делает объявление дорогим, она делает его невидимым. Владелец узнаёт
об этом не отказом, а неделей тишины и решает, что платформа не работает.

Правило появилось 02.09.2026 в `item_set_price()` и до 03.09 знало только
один путь записи из трёх. Измерено на стенде: `insert` с ценой 30 000 000
проходил, прямой `update` на 99 000 000 проходил, и только `item_set_price`
отказывала — то есть **создать можно было то, что нельзя установить**, и
починить собственную опечатку правкой цены тоже было нельзя.

| Где | Что сторожит |
|---|---|
| `assert_item_price()` | публикация (`create_item`) и смена цены (`item_set_price`) — обе двери, обе по-русски |
| ограничение `items_daily_price_max` | прямой `update items` из формы правки объявления |
| `MAX_DAILY_PRICE` в `src/lib/pricing.ts` | форма говорит до отправки, а не после собранных фото |
| `MAX_DAILY_PRICE` в `bot/bot.py` | шаг ввода цены при публикации из чата |

Первые два — рубежи, последние два — вежливость. Меняете число — меняете все
четыре: разойдутся, и форма примет то, что база отвергнет.

Ограничению дано **имя в миграции**, а не оставлено Postgres: на него
ссылаются `humanizeError` в приложении и `CONSTRAINT_MESSAGES` в боте, а
автоимя зависит от порядка колонок.

Проверить, что нигде не забыли, помогает поиск по числу, а не по имени
ключа: значения зашиты цифрами, а не константами с говорящими именами.

### Регулярная задача

`process_overdue_bookings()` двигает сделки, у которых истекли сроки: шлёт
напоминания в день возврата, открывает автоспоры о невозврате, закрывает сделки,
по которым окно претензии прошло без спора. Запускать раз в час.

В Supabase — через **Database → Extensions → pg_cron**:

```sql
select cron.schedule('renthub-overdue', '0 * * * *', $$select process_overdue_bookings()$$);
```

**Проверить, что задача жива:**

```bash
npm run health
```

Это не косметика. На планировщике стоит правило Trust Score, которое лендинг
обещает клиенту словами «Не вернули — спор открывается без участия людей», а
страница для жюри называет реализованным. Не запущен — правило не выполняется,
и узнать об этом можно было только по жалобе участника: схема `cron` через
PostgREST не видна, а запрос для SQL-редактора лежал закомментированным в
`db-tests/90_smoke_live.sql` с 21.08.2026 и не был выполнен ни разу.

`npm run health` заодно показывает то, что тоже живёт снаружи базы: очередь
уведомлений (бот не поднимается сам после перезагрузки), состав витрины,
участников и заявки, которые ждут ответа.

Очередь разделена намеренно. «Ждут доставки» — работа бота, по ним и тревога.
«Без Telegram» — не поломка: человек видит эти уведомления в ленте приложения,
`sent_at` означает только «ушло в чат». Первая версия считала одно другим и
поднимала тревогу на том, что исправно, — а тревога, которая горит всегда,
перестаёт читаться.

**Участники считаются без служебных аккаунтов.** До 04.09.2026 в это число
попадали два тестовых аккаунта и владелец демо-витрины: выходило «8
участников» при пяти живых людях, а привязка Telegram — «1 из 8» вместо
«1 из 5». Ошибка была удобной — пилот выглядел больше, чем есть, — и этим
числом меряют успех и называют его на питче. Служебный диапазон номеров
описан в `shared/service-accounts.json`.

### Кого не хватает в Telegram

```bash
npm run nudge
```

Привязка — условие работы трёх вещей сразу: уведомлений о сделках, ответа
организатора на обращение и входа по коду. Без неё человек пользуется
половиной продукта и не знает об этом.

Дотянуться до него изнутри продукта нельзя: чтобы позвать, нужен канал,
которого как раз и нет. Он есть у организатора — те же номера, по которым
людей приглашали. Поэтому команда не рассылает, а готовит: кому писать, в
каком порядке и каким текстом. Порядок — по числу пропущенных событий: у
кого висят непрочитанные, с тем разговор про его дело, а не про нашу
метрику. Тому, у кого пусто, обещается не пропущенное, а будущее — иначе он
откроет, увидит тишину и в следующий раз не откроет.

## Пассивный режим владельца

Большинство владельцев ведут себя как «помесячные» арендодатели: хотят сдать
вещь и забыть, а не управлять каждой сделкой. Поэтому «Мои вещи» построен как
готовый итог — «вот что произошло, пока вас не было», — а не как дашборд с
контролем. Владельца дёргают только там, где без него сделку не сдвинуть:
подтвердить бронь и принять вернувшуюся вещь. Календарь занятости существует и
показывает реальные данные, но это опциональная деталь, а не то, что владелец
обязан открывать.

Таблица `notifications` — общая точка для приложения и будущего бота: бот
забирает записи с пустым `sent_at` и рассылает их в Telegram.

## Бизнес-модель (расчёты, без реальных транзакций)

- Комиссия платформы: **20%** от `daily_price × дни`
- Страховой сбор: **+150 ₸** фиксированно, если арендатор выбрал защиту
- Владельцу: сумма аренды минус комиссия
- Компенсация ущерба: **отдельной строкой** в `payouts` (`kind =
  'damage_compensation'`), комиссия с неё не берётся

Две строки вместо одной — чтобы владелец в «Моих вещах» видел, из чего
сложилась сумма, и не открывал спор ради этого. Экран показывает
«из них компенсации ущерба» отдельно.

Расчёт продублирован в `src/lib/pricing.ts` — чтобы показать сумму до создания
брони. Авторитет остаётся за базой: клиент не отправляет суммы, их проставляет
триггер из цены объявления.

## Открытые вопросы

- **У арендатора нет механизма на неисправную вещь.** Спор открывает только
  владелец и только после возврата: `open_damage_dispute()` проверяет
  `owner_id = auth.uid()`. Арендатор, обнаруживший, что перфоратор не
  работает, не может ни заявить об этом, ни вернуть деньги.

  Единственная его защита — не нажимать «Я забрал вещь», пока не осмотрел:
  до этой отметки бронь отменяется без последствий. Это работает, и теперь
  об этом сказано и на экране сделки, и в вопросах на сайте. Но это защита
  внимательностью, а не правилом.

  Стоит ли давать арендатору свою претензию — вопрос продуктовый, не
  технический. Плюс: сторона, которая платит, получает голос. Минус: два
  вида споров вместо одного, и почва для отказа платить за нормально
  отработавший инструмент. На пилоте из знакомых людей второе перевешивает;
  на масштабе — вряд ли.


- **Восемь демо-объявлений на витрине и реклама.** Сейчас каталог
  наполнен вещами от «Демо-витрины RentHUB» с нарисованными заглушками
  вместо фото. Пока витрину смотрят свои, это нормально: она показывает,
  как всё выглядит, и заглушки честно написаны словами «фото добавит
  владелец».

  Как только на сайт пойдёт реклама, это перестаёт быть нормальным.
  Человек придёт по объявлению «аренда перфоратора», выберет вещь и
  попробует её забронировать — а владельца у неё нет, и подтверждать бронь
  некому. Бронь провисит в pending до конца срока и закроется сама
  планировщиком: технически всё сработает, а человек решит, что платформа
  мёртвая.

  **Первое из двух сделано 03.09.2026: объявления помечены.** На карточке
  каталога стоит значок «ДЕМО», а на экране вещи вместо календаря и кнопки
  «Забронировать» — блок, который прямо говорит, что подтверждать бронь
  некому, и ведёт обратно в каталог. Выключенной кнопки с мелкой подписью
  тут быть не могло: DESIGN.md требует называть причину недоступности
  заметным блоком, а не серым текстом.

  Признак живёт в `shared/demo-owner.json` — имя служебного владельца,
  которое читают двое: `scripts/demo-listings.mjs`, заводящий и чистящий
  эти объявления, и приложение (`src/lib/demo.ts`). Держать имя в двух
  местах значило бы однажды переименовать в одном: скрипт завёл бы новых
  демо-владельцев, а витрина перестала бы их помечать — и молча вернулась
  бы к тому, из-за чего вопрос и открыт.

  **Второе решение осталось за организатором.** Снимать ли демо-объявления
  перед рекламой — вопрос не технический: пустая витрина отвечает на «а
  есть ли тут вообще перфоратор» словом «нет», и это худший ответ, чем
  честное «вот как это выглядит». Пометка сохраняет показ и убирает обман,
  но живых объявлений не заменяет. Снять всё одной командой:
  `npm run demo:clear`.


- **Фото «до» можно удалить, и это заметно только модератору.** Снимки
  лежат в Storage в папке владельца, и политика `item_photos_delete`
  разрешает ему удалять из неё — правильно для обычной уборки, но у этого
  есть оборотная сторона. Если вещь была повреждена ещё до аренды, снимок
  со сколом мешает заявить порчу: удалил, и сверять «стало» не с чем.

  Закрыть политикой дёшево не выходит: `storage.objects` не знает про
  `items.condition_photos`, а имя файла в бакете и URL в массиве — разные
  строки. Пока сделано то, что можно сделать честно: карточка спора прямо
  говорит модератору, что фото «до» нет, и советует спросить владельца
  перед тем, как удерживать деньги. Отличить «удалил» от «опубликовал без
  фото» база не может.

  Настоящее решение — копировать фото «до» в момент подтверждения брони в
  папку, куда владелец не пишет. Это лишнее место и лишний код, и на
  пилоте из одного города, где участники приходят по приглашению, цена
  выше пользы.


- ~~**Город пилота**~~ — решён: **Кокшетау**. Значение живёт в двух местах,
  и они обязаны совпадать: `EXPO_PUBLIC_PILOT_CITY` в `.env` и дефолт колонки
  `items.city` в базе. Разойдутся — объявления будут создаваться в одном
  городе, а искаться в другом, и витрина окажется пустой при полной базе.
- **Сумма авторешения спора** — платформа удерживает меньшее из заявленного
  ущерба и депозита. Альтернативы описаны в комментарии к
  `decide_dispute_payout()`.
- **Сколько фото требовать** при публикации — сейчас минимум одно; компромисс
  описан над `validateNewItem()` в `app/item/new.tsx`.
- ~~**Часовой пояс дедлайнов**~~ — решён миграцией `20260817100000_deadline_timezone`.
  `(end_date + 1)::timestamptz` брал пояс сервера, а у Supabase это UTC: «конец
  последних суток» вычислялся как полночь по UTC, то есть 05:00 по Кокшетау, и
  дедлайн уезжал на пять часов позже обещанного. Теперь пояс задан явно —
  `at time zone 'Asia/Almaty'`. Стенд проверяет и правильный результат, и то,
  что наивная формула дала бы другой момент.
- ~~**Отмена заявки меняет не только статус.**~~ Закрыто 31.08.2026
  миграцией `20260831110000_lock_cancel_amounts`.

  28.08.2026 отмена переехала в `booking_cancel()`, и вопрос был помечен
  закрытым — преждевременно. Политика `bookings_cancel_pending` осталась на
  месте, а с ней и прямой путь: её `with check` смотрел только `renter_id`
  и `status`, поэтому арендатор мог тем же UPDATE переписать суммы своей
  неподтверждённой брони. **Добавить дверь — не то же самое, что закрыть
  старую**; PostgREST открыт, и обращаться напрямую к таблице никто не
  запрещал.

  Теперь политика удалена, и у `authenticated` не осталось ни одной
  UPDATE-политики на `bookings`: все переходы идут через `security definer`
  функции. Это ровно тот принцип, который заявлен выше как главный, — до
  сих пор он держался на честном слове клиента.

  Стенд проверяет именно прямой путь: `update bookings set status =
  'cancelled', renter_total = 1` не меняет ни сумм, ни статуса. Ждать там
  исключения нельзя — RLS фильтрует строки, а не отклоняет запрос, и без
  политики UPDATE завершается успехом, изменив ноль.
